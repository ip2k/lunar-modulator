# 19 — Effects lookup mathematics

## Reproduced tables

[verified, 2026-09-14] The stock `FM-1_015` application has SHA-256
`306e47065f35d7a7a05ada7f5dd092f6e770952054f33f0a86b75fd10ffe3203`.
Two adjacent tables contain 513 little-endian IEEE 754 single-precision
floating-point values each. Independent formulas reproduce **all 4,104 bytes**,
including the signs of zero. No vendor table payload is included in the tools.

| Table | Application file offset | Runtime address | Formula, i = 0..512 |
| --- | --- | --- | --- |
| Full-cycle sine | `0x53B94` | `0x02053CB4` | `float32(round(sin(2*pi*i/512), 8))` |
| Hyperbolic tangent | `0x54398` | `0x020544B8` | `float32(tanh(i/64))` |

Runtime addresses use the independently checked flash mapping in
[13 — Firmware decoding](13-firmware-decoding.md). The sine's final endpoint
is negative zero; its midpoint is positive zero. The implementation generates
one quarter and mirrors it to preserve these signs without relying on the
host math library's approximation to `sin(pi)`.

The sine is rounded to eight decimal places **before** float32 conversion.
Simply converting the full-precision sine to float32 changes entries. The
hyperbolic tangent uses direct float32 conversion without decimal rounding.

Full table SHA-256 fingerprints:

```text
sine 0e805578a690fbf1eb1eca2bf611e78f6ffedf3cd3a876e76ebb119c56416850
tanh a6c0a24144dc64bc73a4a8955f43e1b5f32f80f61569e33be612c9ac97fcdc61
```

These offsets refer to extracted application bytes, not the outer firmware

## What the match establishes

[verified] The chorus process candidate loads the sine address in the
six-byte immediate instruction at application file offset `0x1D178`.
See [18 — Effects decoding](18-effects-decoding.md) for callback evidence.
The table has 512 phase cells plus a repeated endpoint, a layout suitable for
interpolation across the last cell. Table layout alone does not establish
the interpolation equation, modulation rate, or depth.

The tanh table covers nonnegative input from 0 through 8 in steps of 1/64.
The callback with dispatch ID 3 uses it in the output stage described below.
The callback with ID 5 also reads it in three earlier coefficient calculations
at file offsets `0x1D610`, `0x1D67A`, and `0x1D6E6`; its presence is therefore
not sufficient to assign an effect's name.

`tools/fm1_dsp.py` generates and locates both complete tables. Automated tests
compare the generated bytes with independently measured stock fingerprints,
reject incomplete or changed tables, and verify the material rounding and
signed-zero behavior. These checks establish table contents, not complete
effects behavior or hardware equivalence.

## Tanh output stage in callback 3

[verified] The process callback at runtime `0x0201C8D6` ends at application
file `0x1CFD8`. Its final stage loads the table through base `0x02051D10`
and word indices 2538 and 2539. Since
`0x02051D10 + 2538*4 = 0x020544B8`, these loads address the tanh table and
its next element. The base load is at file `0x1CF8C`; the two element loads
are at `0x1CF98` and `0x1CFA0`.

The effect name **Distortion remains inferred** from the evidence in
[18 — Effects callbacks and state](18-effects-decoding.md). The following
table identifies concrete operations independently of that name.

| Application file offset | Observation |
| --- | --- |
| `0x1CF5E` | Loads float bits `0x44000000`, or 512.0 |
| `0x1CF62` | Multiplies the preceding filter result by 512 |
| `0x1CF6A`–`0x1CF72` | Starts with sign multiplier +1; for a negative sign bit, clears that bit and sets multiplier -1 |
| `0x1CF78` | Converts the nonnegative lookup position to an integer index |
| `0x1CF7E`, `0x1CF86` | Starts with result +1; unsigned index greater than 511 skips table interpolation |
| `0x1CFA4`–`0x1CFB4` | Computes `T[i] + (T[i+1] - T[i]) * (position - float(i))` |
| `0x1CFB8`, `0x1CFBE` | Applies the sign multiplier and a separately computed gain |
| `0x1CFC8` | Stores the output and advances the output pointer by four bytes |

[inferred, symbol-crosschecked] For ordinary finite inputs, the recovered
calculation is:

```text
v = output of the preceding filter stages
position = abs(512 * v)
i = truncate_to_integer(position)
value = 1
if unsigned(i) <= 511:
    value = T[i] + (T[i+1] - T[i]) * (position - float(i))
output = value * sign_multiplier(v) * gain
```

Here `T[i] = float32(tanh(i/64))`. Thus the interpolation approximates
`tanh(8*v)` inside the unsaturated interval. When the converted index exceeds
511, the stage uses exactly 1.0 before applying sign and gain; it does not
read the table's final value as a saturation constant. This produces a small
difference from evaluating `tanh(8*v)` directly near the boundary.

The float arithmetic and conversion interpretation is supported by matching
the same instruction fields in symbolized vendor `__mulsc3`, `__divsc3`,
`_redupif`, and `erfcf` library listings. The vendor disassembler itself prints
these float instructions as unknown halfwords. This is a semantic inference
from register use and known function operations, not a vendor mnemonic or a
measurement of the FPU.

The instructions at `0x1CFB8` and `0x1CFBE` carry the parallel marker. In the
first pair the multiply uses the old `r1` sign multiplier while the companion
instruction loads the gain into `r1`. Treating that pair as sequential would
apply the wrong scale.

The stage's lookup, scaling, sign, interpolation, and saturation paths are now
identified. The complete preceding filters, user parameter-to-gain mapping,
FPU rounding mode, conversion behavior for out-of-range values, NaN handling,
and hardware audio equivalence remain unresolved. The pseudocode describes
operation order; it is not a claim that host double-precision arithmetic will
produce byte-identical samples.
