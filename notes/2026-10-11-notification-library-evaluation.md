# Browser notification library evaluation

**Examined:** 2026-10-11  
**Initial scope:** Research only; no library was installed and no application code was changed on 2026-10-11. The later integration state is recorded below.
**Shortlist prompt:** [Knock’s React notification-library roundup](https://knock.app/blog/the-top-notification-libraries-for-react). It informed the candidate list; implementation claims below come from official project documentation or source.

## Recommendation

The 2026-10-11 research recommendation was to prototype **SweetAlert2 in explicit toast mode** as the first replacement candidate for Lunar’s file notice. That choice has since been wired into the integration worktree and checked in three browser engines; the measured artifact, behavior and validation limits are recorded in [the implementation follow-up](#implementation-follow-up-2026-10-12). It runs without React, declares zero dependencies, supports ESM, and can be self-hosted with its JS and CSS. Its toast mode does not autofocus or block the document. Upstream uses the MIT license. See the [official guide](https://sweetalert2.github.io/), [configuration types](https://github.com/sweetalert2/sweetalert2/blob/main/sweetalert2.d.ts), [release history](https://github.com/sweetalert2/sweetalert2/releases), and [project license](https://github.com/sweetalert2/sweetalert2/blob/main/LICENSE).

Treat toast behavior as separate from accessibility acceptance. A floating message can still be missed. Keep persistent refusal/errors visible in the page’s inline status area, and keep any important action available in its original place. The current integration keeps Undo/Replace/Load-without actions in their native buttons and keeps refusals inline. Do not use SweetAlert2’s modal mode for ordinary status messages.

Web Awesome’s `<wa-toast>` is the stronger alternative if Lunar later needs multiple custom actions inside a toast. It is a maintained, MIT-licensed successor to Shoelace, provides a self-hosted native-module import, a stack, dismissible indefinite messages, a timer paused while hovered or while the close button is focused, and custom action buttons. However, its documented custom-action route uses `allowHtml`; data-derived text must not be interpolated into that HTML without escaping. The component imports icon, progress-ring and toast-item dependencies, and its own docs explicitly describe toast navigation/visibility limits. Review the [toast docs](https://webawesome.com/docs/components/toast), [Core license](https://webawesome.com/license), and [release history](https://github.com/shoelace-style/webawesome/releases) before choosing it.

For any adopted candidate, vendor a pinned release locally and keep its license with the shipped files; do not load a runtime CDN dependency. Verify ESM loading, actual bytes, CSP behavior, repeat/stack behavior, error persistence, browser download flows, and keyboard plus screen-reader announcements. The implementation follow-up below records the checks that have run and the remaining accessibility/deployment limits.

## Pre-integration Lunar behavior (examined 2026-10-11)

`sim/web/www/files.js:486–517` implements one inline notice over the simulator status line. It uses DOM `textContent` for notice and secondary text, creates native action buttons, and appends a Dismiss button. Informational and loaded notices expire after 10 seconds; refused notices remain until dismissed or replaced. The file notice is `role="status"` (`sim/web/www/index.html:104`), while the separate persistent `#status-alert` is `role="alert"` (`index.html:105`). `sim/web/www/app.js:173–178` updates those separately. Thus the file notice is a single inline message slot, not a floating queue.

The file notice action list was limited to one action per notice: Undo load, Replace the clip, or Load without a component. Other editor modules have their own scoped status/live regions; those are task feedback and should not be routed through a global notification library without a separate review.

## Accessibility and deployment constraints

Do not equate an upstream “accessible” or “A11Y-compatible” claim with tested behavior in Lunar. Web Awesome’s documentation gives the clearest cautions: time-limited toasts may be missed, can be difficult for keyboard users to locate, and may cover content; it recommends five seconds or longer and keeping an action available elsewhere. SweetAlert2’s own toast-mode description says toasts never autofocus and do not block the document, which is useful behavior evidence but not a complete AT audit. Test actual live-region announcements, keyboard access to close/action controls, zoom/reflow, and reduced motion with the selected version.

Lunar serves native JavaScript modules and static files; this task found no notification package or React runtime in `sim/web/www`. A locally vendored ESM/CSS distribution is compatible in principle with the static deployment model, but actual GitHub Pages base paths, relative imports, package sub-assets, content-security policy, and offline use must be verified in a prototype. Do not cite CDN examples as offline support.

## Implementation follow-up — 2026-10-12

The integration worktree now vendors SweetAlert2 11.26.25 as unmodified local ESM and CSS with the MIT license beside it; `sim/web/www/vendor/sweetalert2/UPSTREAM.md` records the exact upstream source, hashes and byte counts. The assets total 20,421 gzip bytes (15,387 JS + 5,034 CSS, about 19.9 KiB). The static editor loads them from its own origin without a CDN or runtime package install.

`notifications.js` uses the library for transient file notices. It keeps the notice's original DOM node, text and native action buttons, displays it as a bottom-corner toast for ten seconds, and pauses the timer while a pointer hovers or keyboard focus is inside. Refusals remain in the inline status region and persist until replaced or dismissed. This keeps the refusal workflow visible after a transient notice expires.

The notification-specific Playwright workflow passed in Chromium, Firefox and WebKit in the integration worktree. It exercises focus preservation, a polite nonmodal live region, ten-second expiry, hover/focus timer pausing, native action buttons, plain-text rendering of imported names, persistent refusal behavior, viewport bounds at 1280×800 and 667×375, local-origin asset loading and a restrictive test CSP. The separate full-files browser workflow also passed after its layout predicate was corrected. These are browser automation checks, not a screen-reader or assistive-technology audit.

The shortlist article remains a candidate inventory only; technical behavior and licensing statements above are tied to primary project documentation, source or the measured local asset record. No screen-reader usability, deployed GitHub Pages path, or production CSP audit is claimed here.
