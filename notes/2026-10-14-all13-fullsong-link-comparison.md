# All-13 full-song link comparison

**Status:** bounded offline size experiment only. No production source was changed, no flash layout was admitted, and no device/USB/MIDI/flash/power/reboot action was taken. The initial uncompressed-song comparison below was later superseded by the host-only existing-chunk-codec follow-up; both results are retained for provenance.

## Result

[verified] In the initial comparison, neither optimization linked the 13-production-engine probe with the original 8,888-byte prepared song into the expanded application XIP area. The JieLi linker reported `-Oz` overflow by **1,272 bytes** and `-Os` overflow by **102,320 bytes**. The later host-only chunk-recompression follow-up below reduced that exact song asset enough for a fresh current-source probe to link. Neither link-size experiment resolves physical project-store capacity: app XIP and writable NOR ownership are separate constraints, and no flash bank/layout change is authorized or demonstrated here.

| Variant | Fresh catalogue objects | Sum of object files | Linked `.text` size | Link result | Static arena headroom |
| --- | ---: | ---: | ---: | --- | ---: |
| `-Oz` | 167 | 3,165,512 B | 868,868 B | XIP load image 870,108 B; overflow 1,272 B | 2,320 B |
| `-Os` | 167 | 2,958,100 B | 969,916 B | XIP load image 971,156 B; overflow 102,320 B | 2,320 B |

[verified] The `-Os` output is unexpectedly 101,048 bytes larger in final linked `.text` despite smaller object totals. Both variants independently rebuilt the full catalogue under their respective optimization setting, but this surprising result deserves follow-up before drawing conclusions about compiler optimization behavior. It does not change the immediate result that both links fail.

Both map summaries report `.ram_text` 1,128 B, `.data` 112 B, `.bss` 19,424 B, and 2,320 B between the allocator pool end and guard. This bounded probe does not establish runtime stack safety or audio/perceptual acceptance.

## Runtime and watermark size follow-up

[verified] The existing builder accepts only `diagnostic` and `continuous` runtime modes; there is no `persistent` mode. Diagnostic configures a 20-second return-to-ROM timeout; continuous sets that timeout to zero. Both remain explicitly unadmitted private probes. The optional entry stack watermark is emitted only when `--stack-watermark` is passed. Omitting that option in the private probe does not remove the entry rejection guards: the generated `crt0.S` still checks that the CPU number is zero and that the SPL boot-parameter pointer equals `0x01C7FE08` before setting the app stacks and calling C startup.

The follow-up reused the exact fresh `-Oz` catalogue from source commit e435edadad48641e9e08c0023b71b80b5692cd44, and freshly built the app probe for each runtime/watermark combination. All production IDs, 13 production engines, SAVE service/writer roots, project loader/startup restore, indexed TFT, compressed wavetables, 12 Shapes voices and the same Afterglow payload were retained.

| Runtime | Watermark | `.text` | XIP load image | XIP overflow |
| --- | --- | ---: | ---: | ---: |
| diagnostic | on | 868,868 B | 870,108 B | 1,272 B |
| diagnostic | off | 868,368 B | 869,600 B | 764 B |
| continuous | on | 868,836 B | 870,076 B | 1,240 B |
| continuous | off | 868,288 B | 869,520 B | 684 B |

Compiling out the diagnostic stack painter saves 508 B of XIP image in the diagnostic profile. Switching from diagnostic to continuous saves 32 B with the painter present. Combining both saves 588 B, but the resulting load image still exceeds the region by 684 B. The no-watermark links also report `.bss` cannot be allocated in the XIP load segment after the region overflow; no variant links successfully. This supports retaining the entry guards while omitting watermarking from a release-size build if appropriate, but it does not make this full-song probe fit or provide stack-margin evidence. Watermarking is diagnostic instrumentation, not a release safety requirement.

## Existing chunk codec and host-only recompression follow-up

[verified] The repository already has a LUNARB raw-DEFLATE chunk reader, with per-tag decoded-byte caps and a bounded pull-reader. The on-target inflater accepts dynamic Huffman streams with the format's at-most-4-KiB window; the target binary does not need a new codec or additional RAM for this experiment. `tools/native/recompress_project.py` is a **host-only** utility using Python stdlib zlib raw DEFLATE (`windowBits=-12`, level 6). For each known chunk it tests a bounded zlib candidate, verifies exact decoded bytes and only chooses the candidate when it is smaller than both raw bytes and any already-compressed representation. It leaves non-beneficial chunks uncompressed and copies ancillary unknown chunks as-is. It rebuilds directory offsets/lengths/CRCs/container integrity fields and re-parses the complete output, requiring the canonical records tuple to match. This utility does not change firmware or claim a worst-case compression ratio.

The bounded Hera corpus used CPython 3.11.2 and zlib compile/runtime 1.2.13 in `lunar-recovery-pytest:20261011` (image SHA-256 `7e32dd6d9d02ed13b5d5b1480486e60a0010a8247d7e76c52cb9552c61ce5d`), Docker task limits CPU 1 / memory 512 MiB / swap 512 MiB / network disabled. ## Decision and next dependency

Do not switch to `-Os` as a storage strategy; the initial run gives a much larger final `.text`. Reusing existing DEFLATED chunks on a host is a viable size optimization and can make this particular packed song probe fit the current app area without extra target RAM or a new dependency. It is not a universal fix: retain raw fallback and do not claim guaranteed space for arbitrary songs/projects. The result does not justify changing app feature roots or reducing the engine catalogue. The `.bss` warning is understood as `NOLOAD` section reporting supported by the prior successful diagnostic ELF and explicit startup zeroing, but should remain visible in build logs. The next dependencies are to validate exact sequence/runtime semantics on the target path and independently establish physical layout ownership and bounded SAVE storage/rollback behavior. A one-song link-size probe is not evidence that two project slots fit NOR.
