# Diagnostic Trio pulse readiness origin

[verified] Before this change, `app_main` captured `start = fm1_ms` at entry, then used it for both the overall timed-runtime deadline and the diagnostic pulse offset. The optional compressed-table decode, `fm1_app_init`, engine/pool setup, optional startup content and initial audio refill all happened after that timestamp. Any of those delays shortened or skipped the pulse's ;ßuÁ‚ùÁS5 second window.

[verified] Future builds with `--diagnostic-trio-pulse` now retain the existing runtime deadline origin and set a separate pulse origin immediately after initial app/content setup and `refill_audio()`. The loop passes current `fm1_ms` and that origin to the pulse helper, which computes unsigned elapsed milliseconds. This keeps the three-second wait relative to prepared audio readiness and preserves wrap-safe counter subtraction. The note-on remains a one-shot; if the main loop first polls after the five-second end it emits no note, and an active pulse produces one note-off on the first poll at or after the end.

A Python source-order assertion checks the future app probe captures its pulse origin after initialization and first refill while preserving the separate earlier runtime origin. Existing builder option tests continue to validate that the diagnostic flag is opt-in and constrained to the intended content-free Trio diagnostic.
