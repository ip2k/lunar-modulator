# Event Horizon playback lag: offline source and binary review

**Scope.** Read-only review of source at `7b71d0c625c585ea9f6de3f67fb3e1afb6e3dc4e` and the retained candidate build tuple. No device or USB actions were performed here. This is a diagnosis plan, not a root-cause finding.

## Findings

- [verified] The retained candidate is `song-diagnostic`, `shapes_voices=8`, `instance_pool_bytes=165376`, app size 845,732 bytes. Build provenance binds app SHA-256 `ba46bf0a4d1bda4d604223c658b141b4a9068e37f65afddd998af04d5296cfc8`, ELF SHA-256 `bb69fad7cf662dce19dbf8b265657717d3606404134a1bb68f7635cc8ef48b61`, source commit `43a5a8d77721e58011a00cec782cb64df73a9f86`, and source-tree SHA-256 `389e32d2de3f678acab2cfeae36457dc971f9bfb6cb61a2a843127de90af0f0a`. The request selects project `replacement-showcase-candidate-event-horizon` and companion set `replacement-showcase-event-horizon-companion-set`; the project dependency scan lists ten module IDs (`acid-bass`, `arp`, `chance`, `drums`, `env`, `hall`, `lfo`, `limit`, `sixop`, `trio`). It reports sequence semantics, native playback, installability and hardware test as false. This proves the embedded content and target link identity, not successful playback or 13 simultaneous DSP engines.
- [verified] The source files relevant to the producer/consumer path did not change between the build source commit and review HEAD. At `firmware/native/app_probe.c:97-122`, `render_ticks_max` records the longest individual `fm1_app_render(...,64)` interval; at `:100-109`, the 256-frame platform callback consumes four 64-frame queue blocks. The exact ELF contains `render_ticks_max` at `0x01c0b9bc`, `draw_ticks_max` at `0x01c0c4cc`, and `audio_queue` at `0x01c0a99c`; retained target disassembly confirms the renderer call and max-counter update. These counters were compiled into the installed candidate, but this build did not display or export their runtime values. They cannot explain the owner’s earlier listening result retrospectively.
- [verified] `firmware/native/audio_queue.h:11-18,47-63` defines eight 64-frame stereo blocks. An empty pop writes silence and increments `underruns` once per missing block. At 44,100 Hz (`firmware/third_party/dinghy/src/platform.c:60-62`), one block is about 1.451 ms, the 256-frame callback is about 5.805 ms, and the full queue represents about 11.61 ms. The callback dequeues prepared samples; it does not run the synthesis engine inside the audio ISR (`platform.c:227-250`). A nonzero queue-underrun count would directly account for silent gaps, but current source/build receipts contain no runtime count.
- [verified] Main-loop order is `refill_audio`, `platform_poll`, input/MIDI work, another refill, draw at a 33 ms gate, another refill, then `display_strip` (`app_probe.c:247-312`). `draw_ticks_max` times `fm1_app_draw` only (`:291-308`); it excludes the strip conversion and LCD sync/DMA setup (`:126-138`). The strip converts 3,840 framebuffer pixels before each DMA blit. The LCD path returns while DMA is busy, so this source does not show an explicit wait on every pass. Slow draw or strip work remains a plausible queue-starvation source because it delays the producer, not a demonstrated cause.
- [verified] `fm1_app_render` dispatches each configured sound slot through sequence/event handling, renders active sound engines, then applicable per-sound inserts, master effects, limiter and peak tracking (`sim/web/src/fm1_app.c:3424-3479,3482-3514`). Which engine, note-density or effect path dominates depends on the active project state; module presence in the compiled catalogue does not mean all catalogue modules run simultaneously.
- [verified] `fm1_app_draw` updates the meter from the latest render peak and decays it by 0.6 once per draw (`sim/web/src/fm1_app.c:4492-4503`). Since the native loop schedules draws on a 33 ms gate, intended updates are about 30 Hz. A slow or irregular meter can be consistent with a delayed main loop, but cannot distinguish render cost, draw cost, LCD work or unrelated display behavior.
- [verified] TIMER4 is a 24 MHz source with 24 ticks per microsecond and a 32-bit wrap at about 178.9 seconds (`firmware/third_party/dinghy/hal/fm1_time.h:3-16`). The existing unsigned-difference measurements are suitable for these short intervals. The `-Oz`/LTO pi32v2 build flags are visible in `tools/native/build_application_probe.py:74-80`; size-oriented code generation alone is not evidence that audio deadlines were missed.
- [reported] The owner reports severe lag and poor audio during a two-minute Event Horizon run. [inferred] The queue path makes producer starvation a high-value first hypothesis, while the accompanying meter lag makes the main-loop/render/draw/display boundary worth measuring. Neither observation identifies which stage is at fault. No target timing trace, queue count, source-level hot path attribution or performance A/B was available in this review.

## Next measurement

On the next authorized watched run of the exact same image and content, first capture the existing queue-underrun count, maximum 64-frame render time, maximum draw time, and time spent converting/blitting a display strip, plus an aggregate main-loop/refill interval. Report render time in microseconds (`ticks / 24`). Capture deltas around audio start and PLAY separately if owner observations permit; also record whether host UAC playback/capture is connected, since its 1 ms service can interrupt the audio path (`platform.c:191-217`). Keep the 13-module build, project/set bytes, voices, scheduler, and power/clock settings fixed.

If underruns rise, compare the producer-stage timings against the 1.451 ms block deadline and 11.61 ms maximum queue reserve. If counters stay at zero while audio still sounds wrong, investigate sample correctness, I2S/codec output, levels and actual listening separately. If render fits but draw/strip intervals correlate with queue depletion, the smallest useful A/B is a diagnostics-only display-work schedule change with audio/project/build settings unchanged. Do not reduce the catalogue or default song to make a performance result.
