# Event Horizon note-path audio investigation (offline source review)

Source baseline: `43a5a8d77721e58011a00cec782cb64df73a9f86`, the retained source for the Event Horizon diagnostic image under review. This note contains source inspection only; no device, USB, MIDI, playback, or build operation was performed here.

## Findings

- [verified] The callback and queue agree on frame/channel layout. `platform.c:60-62` sets a 44,100 Hz platform rate, 256 frames per I2S half, and 512 interleaved words. `fm1_alnk0_irq` passes the half-buffer and 256 frames to `app_audio` (`platform.c:227-247`). `app_probe.c:100-109` consumes one 64-frame queue block per loop at `out + i * 2`; `audio_queue.h:10-18,34-66` stores 128 interleaved Q15 `int32_t` words per block and writes stereo samples. Four blocks therefore fill the 256-frame HAL half. No source-level stride or frame-count mismatch was found.
- [verified] The queue is an eight-block, single-core main-loop-producer/audio-IRQ-consumer ring. A missing block becomes silence and increments `underruns` once (`audio_queue.h:10-18,34-66`). Its capacity is 512 frames, about 11.6 ms at 44.1 kHz; one HAL half consumes 256 frames, about 5.8 ms. These are buffering limits, not evidence that the producer meets its deadline.
- [verified] Output scaling is Q15-to-24-bit placement: the HAL applies Q12 master gain, clamps to signed Q15, taps UAC audio, then shifts each word left seven (`platform.c:239-247`). The native image build changes HAL master gain to unity and routes the knob into `lunar_master_raw` (`build_application_probe.py:367-372`); `app_probe.c:278-286` forwards it to `fm1_app_master`, which squares the normalized position (`fm1_app.c:3236-3242`). This preserves a similar knob curve while applying gain in the app. [inferred] The owner's reported knob position near three o'clock can reduce level, but does not explain sluggish response by itself. The shift of a negative signed value is not portable C semantics; this HAL path is shared with the older Trio probe, and target-instruction behavior would need disassembly before treating it as a cause.
- [verified] The app calls `fm1_app_init(&app, 44118.0f)` (`app_probe.c:190`), while the HAL's nominal `FS` is 44,100 Hz (`platform.c:60`). The relative difference is about 0.041%. [inferred] That small mismatch can affect tuning or long-run timing slightly, but does not plausibly explain severe sluggishness on its own.
- [verified] The application render path is materially broader than a one-engine probe. Every 64-frame refill calls `fm1_app_render` in the main loop (`app_probe.c:111-123`). That calls `render_sounds`, which renders every configured sound engine, its inserts and level, sums the units, then processes master effects, limiter, scope/peak and metering (`fm1_app.c:3429-3518`). It does this before PLAY as well as during a sequence. The current Event Horizon project vector contains Drums, Sixop, Trio, Acid Bass, Hall and Limit [verified: `notes/2026-10-14-shapes-voice-cap-options.md:51`]. Thus pressing a key before PLAY still runs the loaded multi-unit project; it is not a single-engine baseline.
- [verified] The earlier `engine_probe.c:27-49` renders one Trio engine in the audio interrupt, with 64-frame chunks. The prior audible Trio result is an owner-reported runtime observation, not independently repeated here. Its source path and CPU workload differ from the new application, even though both share the Dinghy HAL.
- [verified] Existing maxima have distinct coverage: `render_ticks_max` brackets one `fm1_app_render` call (`app_probe.c:111-123`); `draw_ticks_max` brackets `fm1_app_draw` (`app_probe.c:292-308`). It does not include `display_strip`'s pixel conversion/SPI handoff (`app_probe.c:125-138`). The queue's underrun counter is the direct evidence of missed audio blocks; render and draw maxima help localize work but are not total-main-loop or callback-budget measurements. No counter/source mismatch was found in this review.

## Next diagnostic comparison

Use the already reviewed readout on the exact installed source/image and record, while pressing individual keys before PLAY and during the song, the `U` underrun count, `R` maximum render time, and `D` maximum draw time. Keep the master control fixed. Interpret `U > 0` as observed missing queue blocks; `R` near or above the 64-frame interval (~1.45 ms) points toward per-block render cost; low `R` with increasing `U` points toward queue starvation outside that render call, including main-loop work or display/SPI service. `D` does not cover `display_strip`, so do not use low `D` alone to clear display work.

If the key-only case still underruns, compare the same note gesture against a private, one-Trio diagnostic profile through the existing offline build path, without changing the installed image or reducing the shipped engine catalogue. The comparison must preserve the same HAL, sample rate, master setting, and readout. That separates the app's multi-unit idle cost from the core audio path. A source-only or host-render test cannot establish target deadlines, codec output quality, or perceptual acceptance.
