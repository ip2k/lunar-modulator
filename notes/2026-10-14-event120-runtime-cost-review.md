# Event Horizon target runtime-cost review

**Scope.** Read-only comparison of the exact private instrumented Event Horizon pi32v2 target link and the retained Trio-only engine probe. No source, audio behavior, clocks, build flags, or device state were changed here.

## Findings

- [verified] The matched Event Horizon image is the private diagnostic link recorded in [the target build note](2026-10-14-realtime-event120-target.md): app SHA-256 `26f13c5951844de2c98c6dd4b56162674e7c2032b2dba7e6aa4b7f121e9cd2ee`, ELF SHA-256 `4fcf7a2c3be993bc708b2dc48f58e2ee1d90e8d1bb33eb2fbadc21c4d97e1c0d`, and vendor disassembly SHA-256 `f6a2504aaf2ff70383ce84f92e02b0d36da7472149e556683412259e8f8ccc3d`. It retains all 13 catalogue engines, but its Event Horizon project has four active sound slots: drums, sixop, trio, and acid-bass. Its two master slots are Hall and limiter; the four instrument insert pairs are empty. The companion SET and Event Horizon content were linked with the same tuple. Catalogue inclusion is not equivalent to 13 simultaneous renderers.

- [verified] The shared application source constructs a slot for each configured sound, dispatches the sequencer block when `a->seq` is present, and otherwise calls each non-null engine's render method in `render_sounds` ([`fm1_app.c:3429-3479`](../sim/web/src/fm1_app.c)). The render path then runs each configured master effect, the limiter, and per-sample scope/peak tracking ([`fm1_app.c:3482-3514`](../sim/web/src/fm1_app.c)). The Event Horizon SET is linked with this target, so the sequence-host advance/dispatch branch is exercised per produced block. This establishes that PLAY is not the switch that removes the project’s configured render path; it does not establish how much work each engine does internally while no notes are sounding.

- [verified] The target driver requests `fm1_app_render(&app, 64)` in its main-loop queue producer and times one such call ([`app_probe.c:112-124`](../firmware/native/app_probe.c)). The audio interrupt only dequeues four 64-frame blocks for its 256-frame callback ([`app_probe.c:101-110`](../firmware/native/app_probe.c), [`audio_queue.h:11-18,47-63`](../firmware/native/audio_queue.h)). The eight-block queue represents about 11.6 ms at 44.1 kHz; each block is about 1.45 ms. An empty dequeue emits silence and increments the underrun counter. Thus the EH engine work competes with main-loop duties to keep that queue supplied, rather than running in the audio interrupt itself.

- [verified] The retained Trio-only probe uses a different architecture: its interrupt handler drains pending events and calls `lunar_engine_render` in chunks up to 64 frames until the HAL callback's requested frame count is filled ([`engine_probe.c:24-52`](../firmware/native/engine_probe.c)). Its target disassembly shows one indirect Trio engine render call in the callback loop (`native-engines-16-20261012/out/platform-probe/disassembly.txt`, around `0x02001d66-0x02001d74`); the instrumented full-app disassembly retains the much larger `fm1_app_render` body at `0x020577c6` (size `0x2b18`) and the app-specific sequencing, multi-slot mixing, effects, limiter and telemetry paths. The two probes differ in application architecture and likely build provenance, so code size or instruction counts from them are not a valid timing comparison.

- [inferred] The most useful static load contrast is therefore not “13 engines versus one.” It is one Trio render path in the known Trio probe versus a stopped EH project that still advances/dispatches its set host and renders four configured engine slots, mixes them, runs Hall and limiter master slots, and updates output telemetry for every 64-frame block. The project's set density may add work during PLAY, but it cannot by itself explain sluggishness already heard before PLAY. This is a plausible load difference, not proof that any stage misses its deadline.

- [verified] The optimized EH disassembly is useful for confirming retained target control flow, not for deriving cycles here. In particular, the indirect engine calls and vendor-instruction details do not give per-engine worst-case timing without a calibrated target measurement. The build is `-Oz`/LTO; those flags and the target ISA are not a runtime benchmark.

## Smallest useful measurement

First use the existing instrumented EH artifact under coordinator-controlled recovery, if the coordinator elects to run it. Keep the linked content, audio setup, master setting and clocks fixed; record short, separate windows for (1) project loaded, no key, PLAY stopped; (2) one held key with PLAY stopped; and (3) PLAY running. Capture deltas for R (maximum 64-frame render interval), U (missing queue blocks), and D (draw interval), alongside an external audio capture. R above roughly 1.45 ms or a rising U is direct evidence of producer pressure; a sluggish meter with low R and stable U points elsewhere in the loop/display path. These counters are diagnostic signals, not a perceptual pass.

If the first windows localize the pressure to rendering, the smallest reversible follow-up is a diagnostic-only matched A/B that bypasses exactly one selected master effect at a time (Hall, then limiter), with the same content and workload and a fresh artifact for each variant. Compare R/U and external audio, then restore the original configuration. If no single effect changes the measurements, add temporary per-slot render timing to identify which active engine dominates before considering any production optimization. Neither experiment was performed in this review.

## Limits

- [verified] Static source and final target disassembly were reviewed; no timing benchmark, fresh link, installation, device operation, USB/MIDI command, or audio listening was performed in this task.
- [reported] The owner has reported severe lag and a sluggish meter on Event Horizon, including sluggishness before PLAY. This note does not independently validate that listening report.
- [inferred] The four-slot-plus-master-effects path is a stronger baseline-load hypothesis than the song's event density alone, but only the instrumented target counters and controlled audio captures can distinguish render pressure from main-loop/display timing, codec/output problems, or perceptual causes.
- [verified] The diagnostic image remains explicitly non-installable and not hardware-tested; SAVE remains disarmed and release/hardware acceptance remain false as recorded in the build receipt.

## Control level and note-capture context

- [verified] The project session's current sound index is 2, which is Trio in the serialized order (drums, sixop, Trio, acid-bass). That is the selected/edit focus, not a render mask: `render_sounds` still walks every active sound slot. It would be incorrect to characterize this project as “drums only” from the current index.

- [verified] The HAL's original master scaling is explicitly replaced by the diagnostic build script: `master_q12` is fixed at unity, and the HAL's smoothed ADC master reading is redirected to `lunar_master_raw` (`build_application_probe.py:369-372`). The main loop passes that 0–1024 value through `fm1_app_master`; the app sets `gain = position * position` and applies it to each output sample (`app_probe.c:279-285`, `fm1_app.c:3236-3246,3511-3513`). The initial raw seed 512 corresponds to app gain 0.25 until the smoothed ADC path updates; this is not a claim about the steady physical knob value. The platform polls the master ADC in its main loop and applies an 1/8 smoothing step (`platform.c:254-283`). Thus the diagnostic build has one app-level master curve, not both that curve and the original HAL attenuation.

- [reported] The coordinator reports a 145-second six-channel capture from the previously installed image: the submitted notes 60/64/67 remained quiet, input channels 3/4 peaked below 0.000112 with RMS around 0.000024 (about -92 dBFS), with no clipping or ALSA overrun. That capture does not establish that MIDI note events reached the app, and it was not taken from the new instrumented image. Physical R/D/U values are still unavailable.
