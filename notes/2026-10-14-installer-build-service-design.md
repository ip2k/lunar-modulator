# Public custom-image build service design — 2026-10-14

## Recommendation

Keep the installer UI on GitHub Pages and add one small FastAPI application as an HTTP adapter, with Kubernetes Jobs as the durable execution queue and isolated builder. Do not run the compiler from the request handler or use FastAPI `BackgroundTasks`: FastAPI's own docs direct heavy work to a separate job system. The repository has no existing dynamic web application/deployment; its Pages workflow builds `_site` and deploys it with `actions/deploy-pages`, so Pages cannot receive this POST or host the compiler. The LAN stack already documents K8s Jobs, a private image registry, job labels, Grafana/Headlamp inspection, and a `docker-batch.slice` resource policy.

Use FastAPI because the only public input is a strict JSON schema, and FastAPI/Pydantic validate and document such a body directly. Flask is a credible smaller alternative, but this API would need to add strict schema validation itself, configure `MAX_CONTENT_LENGTH` (default is `None`), and select a WSGI server; its development server is explicitly not for production. Starlette's streamed request support is useful if necessary, but adds no validation advantage here. Current official docs/source identify FastAPI as MIT and Flask as BSD-3-Clause. Keep dependencies pinned and audited in a dedicated service requirements lock; this project currently has no server framework to reuse.

## Request and state contract

Accept only `POST /api/v1/builds` with `application/json`, maximum body 64 KiB, an exact schema matching `prepare_demo_selection.py`: integer `version == 1`, the existing module-group IDs, ordered `project_ids`, and integer `startup_index`. Reject unknown fields, duplicate JSON keys, wrong scalar types (including booleans where integers are expected), unknown IDs, out-of-range indices, and excess selection counts before enqueueing. This matches the CLI's current 65,536-byte bounded read and `prepare_selection` validation. No upload, client path, executable, compiler flag, catalogue path/hash, shell string, or image selector is accepted.

Return `202 Accepted` plus an opaque random build ID and status URL. The service records a bounded admission row, then creates a Job from a fixed server-side template: pinned builder image digest, fixed command/argv, fixed toolchain and catalogue versions, fixed namespace, and request JSON as an immutable bounded input object. The worker calls `build_demo_image.py` in a fresh per-job output directory. Labels carry project/session/build ID. The public process gets only namespace-scoped permissions required to create/get/watch/delete these build Jobs and input objects; the build container receives no Kubernetes token. Do not mount host paths or Docker sockets, do not interpolate request strings into a shell, deny network egress for the build pod, run as non-root/read-only where feasible, and use a restricted service account and pod security context. Choose durable result storage (bounded shared volume or object store) before implementing downloads: none is established by this repo's current web deployment or the reviewed LAN service docs. Keep storage private and do not expose a worker's node filesystem.

Use K8s for queued/running/complete/failed state rather than an in-process future. Apply one active build initially, a small fixed queue cap, per-IP and global admission throttles, deduplication/idempotency, a bounded request concurrency, and an expiry policy for Jobs, inputs, outputs, and logs. On full queue return `429` or `503` with retry guidance; never silently create unbounded Pods. Set explicit CPU/memory requests and limits, ephemeral-storage limit, `activeDeadlineSeconds`, `backoffLimit: 0`, `restartPolicy: Never`, and a namespace `ResourceQuota`/`LimitRange`. Calibrate limits from actual clean builds before launch. Add a global cap on active jobs because per-pod limits alone do not bound aggregate cost.

Expose `GET /api/v1/builds/{id}` for state and a narrow download endpoint only for allowlisted receipt/artifact files associated with a completed job. Resolve ID through the persisted job record, never accept a filesystem path. Verify receipt hashes and artifact SHA-256 at upload/download; stream with fixed content type, content disposition, size cap, and short retention. Publish neither build logs nor arbitrary worker files. Do not report a success receipt unless `image.json` exists and validates against the selected profile and the worker's exact app bytes.

## Same-origin and public exposure

The current Pages deployment is static and has no `/api` reverse proxy. A browser page on `github.io` calling a separate API hostname would be cross-origin and require CORS; CORS is not access control or abuse protection. For the requested same-origin browser behavior, serve `/api/*` through a same-origin reverse proxy/custom-domain edge that forwards to the API while Pages serves the static paths, or move both static files and API behind a single owned host. GitHub Pages custom-domain/HTTPS support does not itself supply a programmable reverse proxy. Decide and verify the public hostname, TLS, DNS ownership, proxy behavior, and upstream availability before implementation. The LAN docs state remote mobile access is private WireGuard and do not establish a public inbound route; do not expose the personal cluster without a separate owner-approved hosting/network design.

For an anonymous public service, add edge rate limiting and request body/time limits in addition to app validation. Use no cookie-based authorization; if cookies are later introduced, add CSRF protection. Restrict accepted content types, exact origins, and methods; avoid permissive `*` CORS. Return generic errors, redact request contents from logs, and define privacy/retention for source IP and job metadata. Add abuse protection (e.g. challenge or authenticated quota) before making expensive anonymous builds available. A same-origin proxy makes the browser integration simpler; it does not eliminate public abuse controls.

## Build/result meaning and release gate

`build_demo_image.py` describes itself as a private diagnostic builder, runs `build_application_probe.py` with the diagnostic runtime mode, and its receipt explicitly sets `installable`, `hardware_admitted`, `hardware_tested`, `native_ram_verified`, `native_playback_verified`, and `full_song_default_accepted` to false. This build service may return only a clearly labelled **private diagnostic build** and its evidence. It must not call the output a release, upload/install package, accepted image, or flashable firmware. Do not wire its `app.bin` to any device transport or installer flash action.

Public downloadable/installable artifacts require a separate admission implementation and reviewed gate: accepted selectable default, exact package creation with stock protected components and license profile, package guard/audit receipts, linker/layout and physical flash/storage fit, runtime playback and persistence, owner listening, tested install/recovery/rollback on the authorized hardware, and signed/immutable release provenance. A green private compiler receipt is not any of these gates. Keep a distinct release endpoint/artifact registry and explicit status vocabulary after that work is accepted.

## Evidence and sources

- Repository: `.github/workflows/pages.yml` statically builds `_site`, uploads a Pages artifact, and deploys with `actions/deploy-pages`; no server workflow exists. `HANDOFF.md` says web route/HTTP build service/update transport and full-song/default/physical acceptance remain open.
- `tools/native/build_demo_image.py`: fixed server-side state/toolchain/catalogue CLI paths; request bound 65,536 bytes; selection preparation, native diagnostic link, receipt revalidation, and explicit non-installable status.
- `tools/native/prepare_demo_selection.py`: exact version-1 request keys, ID-based project selection, staged input preparation, hash-verified receipt; no client paths.
- [FastAPI request bodies](https://fastapi.tiangolo.com/tutorial/body/) document Pydantic-model body validation. [FastAPI background tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/) recommend larger job systems for heavy work.
- [Starlette request streams](https://www.starlette.io/requests/) allow bounded streaming without storing the whole body; use a hard cap if relying on streaming.
- [Flask `MAX_CONTENT_LENGTH`](https://flask.palletsprojects.com/en/stable/config/#MAX_CONTENT_LENGTH) is `None` by default. [Flask production deployment](https://flask.palletsprojects.com/en/stable/deploying/) requires a production WSGI server/platform and warns against its development server.
- [FastAPI source metadata](https://github.com/fastapi/fastapi/blob/master/pyproject.toml) declares MIT; [Flask source metadata](https://github.com/pallets/flask/blob/main/pyproject.toml) declares BSD-3-Clause.
- LAN-compute documented platform: K8s Jobs and the aeon cluster image registry; heavy containers go in `docker-batch.slice` with explicit memory and swap limits. For a K8s implementation, [Job docs](https://kubernetes.io/docs/concepts/workloads/controllers/job/) define retries/deadlines and terminal states; [resource docs](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) describe CPU/memory cgroup enforcement; [RBAC guidance](https://kubernetes.io/docs/concepts/security/rbac-good-practices/) calls for namespace-scoped least privilege.
- [GitHub Pages custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages) and [HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https) describe domain/TLS support, not reverse-proxy/API hosting.

## Limits and next implementation slice

This is a design review, not a deployment, security audit, threat-model signoff, or measured resource sizing. No API endpoint, public DNS, ingress, K8s RBAC, runtime image, job, result store, or device transport was created or tested. The actual full build remains unproven end-to-end in the new controller path; the parent-reported 22 focused tests and retained-target link receipt are not evidence that a fresh controller build completes.

Next bounded implementation slice: add a private/local integration prototype for schema validation + one fixed-template K8s Job submission/status/result lifecycle, with fake Kubernetes in tests and no public ingress. First record owner approval for public hosting/networking, settle same-origin hosting and private durable result storage, pin the worker image, and calibrate CPU/memory/storage/time/aggregate concurrency on clean builds; then exercise one fresh controller end-to-end, verify artifact/receipt hashes, restart/recovery/expiry and abuse limits. Only after release admission and hardware/package gates pass should installer download/flash wiring be considered.
