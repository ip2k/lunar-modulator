# Installer preload connection review — 2026-10-14

Scope: read-only review on `feature/2026-10-11@installable-firmware`, HEAD `5967aa5a02852325dbeddce885519309656739ad`. No code/build/transport/hardware changes. This note is the only created file.

## Findings

- There is no native installer route, build service, or web firmware transport in `sim/web/www`. `index.html` and `app.js` are the virtual FM-1. The sole current device API use is `connectMidi()` (`sim/web/www/app.js:989-1012`): `navigator.requestMIDIAccess()` attaches MIDI **inputs** only; it does not request SysEx, enumerate outputs, send a package, or flash. UI calls it “Connect MIDI input” (`sim/web/www/index.html:59`). No WebUSB/WebSerial code was found in that web tree.
- The chooser is deliberately disconnected. `mountNativeDemoSelectionView()` is documented as request-only and leaves build/transport to the caller (`sim/web/www/native-demo-selection-view.js:1-4,35-42`). It displays catalogue estimates and pending full-song disposition (`:65-75`); it does not mark a default or admission. `buildNativeDemoSelectionRequest()` emits the backend’s immutable v1 request with selected module groups, project IDs and startup index (`sim/web/www/native-demo-selection.js:51-73`). Its tests exercise the view and request, not a route or transport (`sim/web/test/native-demo-selection-view.test.mjs`, `native-demo-selection.test.mjs`).
- The first backend seam already exists: `tools/native/prepare_demo_selection.py:22-75` accepts IDs, exports pinned project sources, stages source bytes inside a fresh output directory, prepares/hash-verifies profile inputs and returns `selection.json` with `installable=false`, `native_link_verified=false`, `native_ram_verified=false`, `hardware_tested=false`. It is an offline CLI, not an HTTP service.
- `tools/native/build_application_probe.py:152-207,357-368` consumes a prepared profile only when paired with the retained `profile.json` SHA, links embedded content, and can link/choose a startup PROJECT loader. It is explicitly a timed probe: `--runtime-mode` defaults to diagnostic (`:141-143`), and its own notes say the tested links are not installable and playback is unverified (`notes/2026-10-13-native-image-builder.md:231-248`). This is useful as an integration/evidence seam, not a release artifact generator.
- `tools/native/ota_candidate.py` is an offline private 20-second prototype composer pinned to one stock container and one app hash. Its own module/receipt deny physical boot, recovery, web install and release readiness. It cannot simply wrap arbitrary profile-linked apps. `tools/jieli/package_guard.py` is a required packaging guard for stock SPL, `isd_config.ini`, `ota.bin`, `cfg`, and forbidden loader binaries; it is a packaging prerequisite, not a flasher or release admission.
- The established browser capability already present in this codebase is the Web MIDI API. Reuse that platform API for a later MIDI/SysEx transport adapter if the confirmed FM-1 update protocol supports it, with explicit MIDI output and SysEx permission and a reviewed transfer protocol. The simulator’s current API integration is input-only; there is no reason to add a new UI framework for the chooser. A service still needs to run the pinned native toolchain/build and return a hash-bound artifact; ordinary static browser JS cannot invoke these local Python/toolchain CLIs by itself.

## Smallest credible connection path

1. Add a separate installer composition entry that loads the generated module and demo catalogues/default profile and mounts the existing chooser. Its callback may submit only the versioned request; keep filesystem paths, source hashes, packed bytes, toolchain paths and expected profile digest backend-owned.
2. Add a bounded build-service adapter around `prepare_demo_selection.py`; retain the returned manifest digest, invoke a **release-capable** native builder with that exact prepared profile and startup project index, and return only a complete hash-bound build receipt/artifact. The existing `build_application_probe.py` can prove content/profile linkage during integration, but cannot be labelled installable until a release target/package path replaces the diagnostic probe and passes exact image/license/flash/RAM/timing guards.
3. After artifact admission and separate physical acceptance, connect the web installer UI to a dedicated, reviewed update transport adapter. Reuse Web MIDI output only after confirming the protocol; gate “Install” on complete artifact/package evidence and the required owner-authorized physical admission. Keep the stock boot components and recovery safeguards enforced by the existing package guard and campaign policy.
4. The default image cannot be set by chooser metadata. The catalogue currently reports `full_song_default` pending and has no admitted default (`HANDOFF.md`, 2026-10-14 selectable demo catalogue checkpoint; `notes/2026-10-13-native-image-builder.md:258-268` says production default content starts empty). First choose/review a complete song and resolve its exact modules, embedded bytes, link/RAM fit, native full-length playback, and save/reload; then encode it in the production default profile while retaining all thirteen production engines.
