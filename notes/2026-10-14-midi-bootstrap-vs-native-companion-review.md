# Expanded update transport: MIDI bootstrap versus native companion

**Status:** offline feasibility review, 2026-10-14. No USB/MIDI/device command, flash write, install, reset, or implementation occurred. The expanded candidate and transaction remain noninstallable and physically unadmitted.

## Recommendation

Prefer a native host companion using the already-reviewed fixed ROM loader transaction as the next transport implementation. Treat a stock-OTA-installed MIDI bootstrap as a later, separate product experiment, not as a reuse of the current writer. A bootstrap could accept a byte stream in principle, but the repository has no application MIDI SysEx install protocol, no admitted application NOR writer, and no safe way yet to execute an app that is overwriting its own XIP image. Those are substantial new firmware and recovery problems. The existing native path already performs full-image backup/readback and journaled sector transactions through the ROM loader; its current weakness is that the live adapter is Linux SCSI Generic, while the owner operates from macOS.

The next bounded implementation should therefore make the native host transport portable to the owner's platform (or define a small local companion boundary with an explicitly reviewed macOS USB backend), leaving the transaction, image receipt, sector allowlist and journal policy unchanged. First make a transport-fake contract test for the current `NativeSession` calls and interruption/resume checkpoints; then implement only an offline/native transport adapter against that contract. Do not add WebMIDI or firmware-side writes until the owner chooses to invest in a bootstrap and approves its firmware/recovery scope.

## Existing path and hard constraints

`tools/native/expanded_sg.py:75-109` permits only exact `FC0A` JEDEC/liveness, aligned 256-byte `FD05` reads, `FB01` 4 KiB erase and `FB04` target/baseline 256-byte program pages. The guard pins the current transaction intent, exact allowed sectors and page payload; `exchange` binds the open character device to the expected SG node and USB/sysfs mapping, caps commands/time, logs no-retry submissions, and latches ambiguous errors (`:62-73`, `:111-128`). `tools/fm1_bound_diagnostic.py:163-225` supplies the common wire builder and aligned reads; `:233-246` runs `fm1_flash_transaction.run_transaction` and always closes the session.

`tools/fm1_flash_transaction.py` seals two equal complete 1 MiB backups, target, baseline/target hashes, identity, authorized ranges and sector ordering. Before every mutation it durably records direction and intent; it pre-reads, erases and programs exact sectors/pages, then rereads the written data and the complete image. Errors become `recovery_required`; resumption requires a fresh binding and full readback. The expanded plan pins the exact `FM-1_092`, JEDEC `0x856014`, candidate and receipt; it allows 213 changed sectors for the native candidate and puts directory sector `0x4000` last. This is strong host-side transaction structure, not a guarantee that the old application remains bootable during an interrupted expanded write.

The target-side options do not currently offer an alternate writer:

- `firmware/native/midi_stream.cpp:18-20,40-57` configures a 16-byte SysEx parser but returns only channel voice messages (`type < 0xF0`); `firmware/native/midi_input.h` likewise accepts only note, control and pitch messages. Lunar has no firmware install receiver or command layer.
- `firmware/third_party/dinghy/src/ota.c:3-20,147-161` implements a different SysEx protocol for stock update: pack-7 framing, `00 59`, length and additive checksum. It requests package bytes from the host, stages only the update loader at `0xE0000`, writes an update record at `0xE4F00`, then commits/reset (`:350-390`). It does not receive an expanded raw image or write its application sectors. Its source belongs to the GPL-3.0-only Dinghy profile.
- The source HAL `firmware/third_party/dinghy/hal/fm1_flash.h:38-54` allows legacy Felucca data/global and OTA-staging ranges only. The retained all13 SAVE-scheduler ELF has erase/program stubs that return `-1`, as documented in `notes/2026-10-14-native-nor-hal-audit.md`; no admitted Lunar application writer exists. Even enabling that HAL requires a new profile, XIP-off call-graph audit, exact interrupt-state preservation, error propagation, watchdog handling, and readback gates.
- Stock OTA is limited to the 581,564-byte app extent and known loaders write only `[0x4000,0x93000)`. The expanded app is 862,272 bytes and profile reaches `0xD9000`; see `notes/2026-10-14-expanded-fwsc-transport-design.md`. Stock package transport cannot carry the expanded layout.

## Recovery semantics and the bootstrap hazard

The existing ROM transaction can restore the exact baseline from its two backed-up images after an ambiguous failure, provided the unit can be re-entered into ROM and the native host transport remains usable. Its host journal and final whole-image comparison are not stored on the pedal. The candidate protects stock SPL/OTA/cfg ranges and writes the directory sector last, but sectors containing the old application are still changed before the final sector. Therefore directory-last alone does **not** establish that the prior app continues to boot after interruption; recovery may require the ROM path and exact stock restore.

A MIDI bootstrap would have to remain operational while the transaction replaces the app's XIP image. The current HAL executes short code from RAM only while XIP is off; the overall Lunar app and installer would remain XIP-resident. No reviewed staging area is available to hold an independent persistent updater: the OTA region is owned by the stock update flow, and the SPL/configuration regions remain protected. A design that streams/erases the currently executing image needs a separately proven RAM-resident finalization/exit path or an independent execution bank. Neither exists in the inspected source/receipts. The target's combined-RAM linker layout is 432 KiB; the 862,272-byte app is larger than RAM, so simply copying the full stage into RAM is not an option. Existing successful all13 expanded ELF/app artifacts show a 1,128-byte RAM-code segment and roughly 19 KiB BSS for the demo runtime; these figures are not a bootstrap memory budget and no bootstrap link measurement exists.

## Why the native companion is currently narrower

The offline native ROM route already has the operations and policy needed for a full target: complete 1 MiB reads, identity/JEDEC binding, no-retry erase/program commands, precise target/baseline pages, a persistent host-side journal, full readback and stock restoration. It does not depend on Lunar booting or parsing MIDI. The present implementation is specifically Linux SG_IO and verifies `/dev/sg` character-device/sysfs identity; it is not a macOS implementation and cannot be assumed to run on the owner's Mac. A native companion is feasible only after the exact macOS USB transport, interface claim/driver interaction, exclusive ownership, permissions and disconnect/reconnect behavior are reviewed and fake-tested. The browser cannot directly claim the ROM's protected USB mass-storage interface; ordinary direct WebUSB MSC remains excluded.

## Concrete next implementation

1. Extract a narrow transport protocol contract from `NativeSession` (`binding`, `exchange`, `close`) and add fake-transport tests covering command encoding, no retries after ambiguous completion, lost-connection recovery through a fresh binding, and transaction journal resume. The tests must preserve `hardware_admitted=false` and must not invoke a system USB API.
2. In a separate review, determine whether the macOS host can safely expose the FM-1 ROM MSC device to an unprivileged local helper while avoiding the mounted-storage driver. Identify the exact API/driver claim path and release behavior; do not probe a connected device as part of this research.
3. If a reviewed host API is available, implement an isolated native adapter that returns only the exact injected transport shape; keep all immutable image, backup, receipt, identity and sector policies in the existing transaction layer. Otherwise retain Linux-only native tooling and request owner direction on platform scope.
4. Defer the MIDI bootstrap until there is an explicit firmware design for SysEx framing, immutable artifact identity, exact changed-page admission, local durable host journal, application self-overwrite/finalization, stock-ROM recovery and settings migration. Its first check would be a separately built bootstrap footprint in the actual 581,564-byte stock slot plus a RAM-resident erase-to-reset proof; a source-level parser or fake MIDI test cannot satisfy that gate.

This review establishes a design recommendation and source-level constraints only. It does not establish macOS API feasibility, bootstrap size, actual device compatibility, physical write/recovery behavior, setting migration, playback, release admission or installability.
