## What differs in the audio path

[verified] Both binaries use the same native engine interface and Dinghy HAL lineage, but the audio scheduling differs. In `firmware/native/engine_probe.c:22-51`, the earlier probe applies queued MIDI events and calls `lunar_engine_render` directly from `app_audio`, in 64-frame slices until the 256-frame callback is filled. Its retained target disassembly has `lunar_engine_render` at `0x020037b0` and an indirect call through the Trio engine's render function. This path keeps engine DSP inside the audio interrupt.

[verified] In the frozen full app, `firmware/native/app_probe.c:111-134` makes the callback dequeue four already-rendered 64-frame blocks. The main-loop `refill_audio` instead calls `fm1_app_render(&app, 64)`, converts/publishes each result through `lunar_audio_push`, and tries to fill the eight-block queue. The retained app disassembly has `fm1_app_render` at `0x02050db0` and `refill_audio` calling it at `0x020539d4`. Therefore the callback work is deliberately small, while rendering depends on the main loop producing blocks before the queue empties.

[verified] The frozen build does not run thirteen engines. `app_probe.c:289-290` selects one Trio in sound slot 0 when no startup project is compiled in. `fm1_app.c:3433-3457` visits the four sound slots but invokes a sound renderer only when that slot has an engine. The content-free profile therefore exercises one selected sound engine; the other catalogue engines are linked, not rendered. This is not comparable to the four-sound Event Horizon project that prompted the earlier report.

[verified] The full app adds per-block application work around the engine: sound-slot setup/dispatch, optional inserts and master effects when configured, limiter, scope/peak tracking, gain and arpeggiator polling (`fm1_app.c:3429-3525`). In this content-free startup, only Trio is selected and no project/SET is loaded. This establishes a different call path, but source structure and instruction count do not establish that the added work is large enough to cause underruns.

[verified] The eight-block ring has 64 frames per block, or 512 frames total (`audio_queue.h:11-18`). At the initialized 44,118 Hz engine rate, that is about 11.61 ms of queued audio. The HAL callback requests 256 frames, consuming four blocks about every 5.80 ms (`platform.c:63-65,230-253`). A missing block produces 64 frames of silence and increments `underruns` (`audio_queue.h:47-63`). This gives the producer finite headroom; it is not a measured latency or deadline result.

## What the current measurements can and cannot diagnose

[verified] The frozen app's `R` readout is the maximum elapsed time around one call to `fm1_app_render(64)` (`app_probe.c:122-134,358-359`). The nominal time for 64 frames at 44,118 Hz is about 1.45 ms. `U` is the cumulative number of missing 64-frame blocks. If `R` approaches/exceeds 1.45 ms, the per-block render is a likely contributor; if `U` increases, queue starvation is directly observed. A high `R` does not prove starvation because rendering can catch up when the queue has headroom; a low `R` does not clear main-loop stalls.

[verified] `R` excludes the Q15 conversion and sample copy in `lunar_audio_push` (`audio_queue.h:34-45`), plus input polling, MIDI dispatch, draw, and TFT strip conversion/transfer. The separate `D` timer wraps `fm1_app_draw` only (`app_probe.c:349-376`); `display_strip` runs after it and is outside `D` (`app_probe.c:378-379`). The HAL runs a 256-frame callback and performs output gain/conversion/UAC tap after `app_audio` returns (`platform.c:230-253`), but the current readout does not measure callback duration. Thus R/D/U is diagnostic evidence with bounded coverage, not a complete CPU budget.

[verified] The HAL uses a 256-frame, 44,100-Hz I2S half (`platform.c:63-65`) while the app is initialized at 44,118 Hz in this build family. The app engine rate corresponds to the nominal 44,117.6-Hz audio clock documented in `firmware/third_party/dinghy/src/usb.c:64-72`; the 18-Hz difference is about 0.041%. This is not evidence for a severe timing mismatch. `FM1_TICKS_PER_US=24` in `fm1_time.h:16` is the timer conversion constant, not a verified measurement of CPU clock frequency. The code search/source review found no positive evidence in this path that the frozen app configures a different CPU clock from the earlier probe.

## Evidence-ranked diagnosis and next experiment

[verified] No callback frame count, interleaved stereo stride, queue publication, Q15 conversion, or HAL half-buffer mismatch was found in the inspected paths. The most concrete architectural difference from the earlier clean-note probe is moving the engine render from the IRQ into main-loop production, then adding the app wrapper and ring conversion. [inferred] If the key path sounds laggy or breaks up in the frozen content-free build, main-loop starvation or a different app-level note/gain path is more plausible than thirteen-engine load, because this build renders only Trio. This remains a hypothesis until target counters and captured audio agree.

[verified] The best bounded discriminator is the installed frozen build's own R/U readout during a held note and simultaneous analog capture, with the master position held fixed. Record R, U before/after, pulse timing, capture RMS/peak and note onset. If U rises, the producer missed blocks; R near the 1.45-ms block period points toward render cost. If U remains flat and captured audio is quiet, investigate note dispatch/gain/analogue path rather than optimize the renderer based on code size. If U stays flat but note onset trails input, measure event-to-first-render queue latency; the queue can contain up to eight blocks before an event is applied.

[inferred] A useful follow-up A/B, if the current observation remains ambiguous, is to build a private one-Trio direct-ISR probe and the content-free app with matched engine object, sample rate, HAL, note sequence and master gain, then compare R/U and captured analog output. The existing old probe is not itself a controlled baseline because it predates the frozen source/profile and uses a different path and build inputs. Do not infer an engine-count or shipped-catalogue limitation from this diagnostic comparison.
