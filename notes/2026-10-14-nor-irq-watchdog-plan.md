# NOR RAM wait: IRQ-state and watchdog contract

**Status: design research only; no HAL changes and no device validation.** Source base: `7f370e20db135432b50db2598e4f72e3c39a1802` (`codex/2026-10-14-nor-irq-watchdog-plan`). The immediate issue is not resolved for production admission. The current NOR path can keep executing from RAM while XIP is disabled, but the firmware has no demonstrated interrupt-state restoration or watchdog/reset policy that is safe while the NOR may remain busy.

## Evidence reviewed

- `firmware/third_party/dinghy/hal/fm1_flash.h` documents its entry points as requiring interrupts already disabled. Its defaults issue `cli`, then later issue `csync; sti`; the helper pair does not save/restore the incoming processor status. Consequently it can enable interrupts on return even when the caller entered with interrupts disabled. This is a concrete source-level contract mismatch. For this task I made no code change.
- `firmware/third_party/dinghy/hal/fm1_irq.h` exposes `fm1_irq_off()`/`fm1_irq_on()` using `cli` and `csync; sti`; it has no save/restore helper. `fm1_irq_enable_all()` sets ICFG bit 8 and enables interrupts. `crt0.S` reads `icfg` and `psr` before `cli`; `fm1_vec.S` saves `psr` in the exception diagnostic frame; `fm1_isr.S` pushes and pops `{psr, rets, reti}` around C ISR bodies. These establish accepted syntax and current use, not the precise pi32v2 PSR interrupt-mask semantics or whether restoring a saved whole PSR is safe in this context.
- The pinned toolchain at `/home/claude/mvave-fm1/sdk-v1213/toolchain/jieli-linux-toolchains-20250324.1` reports clang 4.0.1, target pi32v2. The project’s target build uses `-target pi32v2 -mcpu=r3 -mfprev1`. I found no authoritative pi32v2 ISA reference in the pinned SDK. The official SDK docs describe watchdog APIs and reset behavior but do not define pi32v2 PSR layout or interrupt-state save/restore semantics.
- `firmware/third_party/dinghy/hal/fm1_sys.h` implements P33 watchdog access: WDT_CON is P3 address `0x80`; feeding ORs `0x40`; startup arms `0x0D` (8 s per the matching SDK header `source-sdk/include_lib/driver/cpu/wl82/asm/wdt.h`). `fm1_cstart()` calls `fm1_wdt_arm(0x0D)` before IRQ initialization. `platform.c` and `recovery.c` feed during normal loops and fault display. The NOR wait loop does not feed the watchdog. The P33 helpers are ordinary C and their own transfer loop has a finite iteration counter; they are not currently annotated/verified as a complete RAM closure.
- The pinned SDK example `source-sdk/apps/common/example/peripheral/wdt/main.c` shows an independent task feeding the watchdog and deliberately demonstrates reset by withholding feeds. Several SDK update paths call `wdt_clear()` around NOR IO; these are call-site precedents, not proof of the FM-1's device-specific driver behavior or safety while this project has XIP disabled.
- JieLi’s official AC79 WDT guide documents watchdog timeout/reset APIs and notes SRAM exception handling for flash failure: [JieLi AC79 watchdog guide](https://doc.zh-jieli.com/AC79/zh-cn/master/module_example/system/wdt.html). It does not establish that a watchdog reset during a NOR WIP interval leaves this board able to boot safely. The published pi32v2 page found during research is third-party and therefore not used as ISA authority.

## Safe contract that can be stated now

1. The NOR routine is entered only from a quiescent context with interrupts already disabled, no ISR/other core touching P33/SPI/SFC, stack and all arguments in SRAM, and all XIP/cache/SFC helpers in the audited RAM closure.
2. While XIP is off, the routine never executes `sti`, restores the XIP mapping, or returns unless it has completed a status transaction that observed WIP clear. Transport failure and a stuck-WIP condition cannot be converted into success by a deadline.
3. On a verified-ready exit the routine returns with interrupts still disabled. The higher-level caller may later restore its prior execution state only through a separately verified interrupt-state protocol. Until pi32v2 PSR semantics are authoritative, do not read/modify/write PSR based on a guessed bit layout and do not claim exact prior-state restoration.
4. All watchdog-feed code used during the XIP-off interval, if adopted, must itself be included in the RAM closure: P33 transaction helpers, constants/literals, stack, and timeout handling. Audit final linked target symbols and disassembly; source section attributes alone do not prove this.

## Watchdog decision remains an admission blocker

There is a real policy conflict. Leaving the current 8-second watchdog unserviced may reset the CPU while NOR is still busy; no local evidence proves that the chip can safely restart/XIP-read in that state. Feeding the watchdog from the RAM wait loop avoids that immediate reset but can keep a permanently busy/unreadable device stuck indefinitely and can mask a software hang. Disabling the watchdog around the operation has the same indefinite-wait problem and adds a period with no watchdog protection. No option is presently established as safe.

Do not add unconditional watchdog feeds, disable the watchdog, or deliberately permit reset during WIP as an inferred fix. Before choosing, obtain authoritative device-specific evidence or conduct the owner-approved staged hardware validation for reset/power-loss during each erase/program phase with recovery observation. A conservative interim admission rule is to leave the runtime writer disabled. If diagnostic testing proceeds, retain external power control/recovery readiness and treat any busy timeout as a non-returning fail-stop; this is not release acceptance.

## Required next verification

- Obtain JieLi pi32v2 ISA documentation or an independently reviewed ISA source for PSR read/write behavior, interrupt enable/mask fields, instruction barriers, and exception/return semantics. Then compile a tiny target probe and inspect vendor disassembly; that proves compiler encoding only. Validate actual effect through a suitable instruction-accurate emulator or controlled hardware test before advertising exact restore semantics.
- Add stateful host tests for entry already-disabled/nested-disabled semantics, and no enable before verified-ready. Host mocks cannot establish CPU status-register behavior.
- Build the final pi32v2 app and inspect the full call/data closure for every instruction, literal, helper, stack access, and peripheral path used after XIP-off. Repeat whenever the watchdog or IRQ implementation changes.
- Define a watchdog policy from measured worst-case chip erase/program times, maximum legitimate operation duration, and the selected recovery behavior. Test timeout just below/above the limit, persistent WIP, repeated status transport errors, watchdog expiry at each operation phase, reboot reason, and recovery boot. A timer-based host test proves software branch behavior only; it cannot prove actual reset/NOR interaction.

## Limits and confidence

The wrapper mismatch, 8-second startup watchdog setting, and source call sites are directly verified in the pinned project/SDK source. Clang version/target flags are verified locally. Current docs establish general WDT behavior only. No official pi32v2 PSR semantic document was found; assembler acceptance/current disassembly must not be upgraded to ISA proof. No firmware was built for this task, and no hardware, watchdog reset, erase, program, boot, or recovery experiment was run. This note does not authorize a device operation or admit the writer for release.
