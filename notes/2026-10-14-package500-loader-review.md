# Stock-loader acceptance review: private FM-1_500 D7000 candidate

2026-10-14. Read-only review of the offline composer and its exact candidate. No transport, device command, flash operation, or installation was performed. The question here is stock-updater/loader acceptance, not whether the container is structurally well-formed.

## Result

The candidate passes the checks implemented by the local generic FWSC reader and the strict 092 nested-layout model, with the target app and receipts pinned by SHA-256. This establishes byte-level correspondence and format invariants only. It does **not** establish that the currently installed app accepts step 1, that the proprietary OTA loader accepts/writes the expanded D7000 image, or that the new app boots.

## What the evidence covers

The composer checks the exact source FWSC, app, ELF, artifact receipt and build receipt. It requires explicit application identity `FM-1_500`, recovery identity `FM-1_000`, and SAVE disarmed/unadmitted. It invokes the pinned 092 model with one lock-scoped exact app-hash substitution, emits the modeled nested image, then changes only the 20-slot outer physical identity marker. It reopens the output with `inspect_fwsc`, checking outer identity, header/list/payload CRCs, then normalizes the marker and checks exact equality with the strict nested model. The model preserves the decoded SPL, `isd_config.ini`, `cfg_tool.bin`, `cfg`, and key MAC descriptor; the `ota.bin` payload is preserved as part of the normalized outer model. The exact implementation is in `tools/jieli/compose_500_d7000_candidate.py` and `tools/jieli/model_092_app_replacement.py`.

The D7000 profile is internally consistent with the modeled FM-1_092 layout: the first flash-entry extent is `0xD7000`; the expanded nested PRCT record reaches `0xD9000`; VM begins at `0xD9000`, with BTIF and USR after it. This is bounded against the known 092 container profile, not a general-purpose packager. A pre-existing 092 device/install is useful precedent for a moved partition table, but does not show that this exact 500 app or 978,484-byte container traverses the owner’s current verifier and loader path.
