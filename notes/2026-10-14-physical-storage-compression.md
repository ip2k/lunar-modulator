# Physical flash compression research — 2026-10-14

## Decision

**Compression can reduce typical project bytes, but it cannot safely shrink the two-slot storage guarantee.** Keep the current 98,304-byte accepted payload ceiling and raw fallback. No physical project extents are admitted, and the hypothetical 144 KiB aggregate does not own two contiguous 100 KiB slots. Prefer evaluating the existing FM1 raw-DEFLATE chunk format and compressor before considering another dependency. The compact native SAVE build deliberately excludes that compressor path because its memory profile is incompatible with the existing bounded writer workspace; the reader already understands those compressed chunks.

Each transactional slot is 102,400 bytes (32-byte store header plus up to the 98,304-byte project payload). Two need 204,800 bytes. A hypothetical 147,456-byte aggregate is short by 57,344 bytes. A lossless compressor has inputs whose encoded size is at least the raw size; neither a ratio threshold nor a library can guarantee fitting those states into smaller slots. The safe choices are raw fallback with existing capacity, or an explicit smaller supported-project limit enforced before SAVE and LOAD. Compression is not a substitute for an admitted physical map.

## Incumbent implementation and alternatives

| Option | Licensing, API and footprint evidence | Decision for project storage |
|---|---|---|
| **Existing `engines/state/fm1_deflate.[ch]`** | MIT, raw DEFLATE, no heap/libm, deterministic fixed-Huffman compressor, 4 KiB window. The state reader already accepts DEFLATED chunks: stored bytes contain declared uncompressed length plus raw DEFLATE; per-kind caps bound output, 64-byte pull reads feed a 4 KiB inflater window, and CRC covers stored bytes. The reader checks the chunk and stream termination. Tests include malformed/capped DEFLATE cases. | Best starting point: this format already exists and has compatibility/tests. Native compact SAVE excludes the current compressor branch and large buffers intentionally. Re-enabling whole-file compression is not justified by results: target measurement gives a 284,884-byte noncompact writer workspace, while project SAVE leases the compact writer from framebuffer memory and only 2,320 bytes of linked-global RAM headroom exists. Do not assume the noncompact writer or its 32 KiB compressor scratch plus roughly 64 KiB compressed-output buffer can be leased. A bounded compact-chunk adapter would need a separate design and exact target RAM/stack/code measurements. |
| **Vendored `firmware/third_party/tinf`** | Already present and pinned (`57ffa1f1d5e3dde19011b2127bd26d01689b694b`), zlib license; selected for startup wavetable decode. Its one-shot `tinf_uncompress(dest, destLen, source, sourceLen)` API expects an in-memory destination and is not a streaming flash-backed project reader or compressor. The upstream README calls out future work to pass state instead of using over 1 KiB stack and blocking support. | No unmet need for general inflate: the project reader already has a pull inflater. Do not substitute this one-shot API for project storage. It remains appropriate for the existing bounded wavetable use. |
| **LZ4** | BSD-2-Clause. Current upstream documents streaming/frame APIs and `LZ4_compressBound`; the raw block API's worst-case bound for 98,304 bytes is 98,705, above this project's 98,304-byte cap. The current research measured host liblz4 1.9.4, not target code/stack. | Measured faster-style block candidate, but little case for adding a second project codec while the incumbent format is already readable. Frame/block framing, bounded history and caller-owned workspace still need target audits; raw fallback remains required. |
| **heatshrink** | ISC, incremental/static allocation and bounded incremental work. Upstream reports low memory, while optional index adds `2^(window size+1)` bytes plus a temporary 512-byte stack build. No exact FM1 target measurement or output cap was established. | A possible future low-RAM alternative only if the incumbent cannot be fit. No evidence presently warrants another codec or a format migration. |
| **zlib / miniz** | Host measurements here use Python's zlib 1.2.13; they are not target codec measurements. zlib's stream API and raw DEFLATE can interoperate with the existing container, but code/workspace fit would still need target measurement. miniz was not benchmarked or linked. | No reason to add either: existing raw-DEFLATE compressor/reader address the format. Host zlib ratios cannot be attributed to the FM1 compressor, which is deterministic greedy/fixed-Huffman and only compresses in the desktop/simulator writer. |

Current writer behavior matters: the noncompact desktop/simulator writer only tries DEFLATE for chunks when `FM1_STATE_BIN_DEFLATE` is set and no random-access callback is in use. It stores compressed form only when `(compressed_size + 4) <= 75%` of raw chunk size; otherwise the chunk remains raw. `FM1_STATE_BIN_COMPACT_WRITER`, required by native project SAVE, removes the large buffers and excludes this compressor path. This is a workspace/design boundary, not missing decompression support or proof that compression cannot work in a future compact design.

Relevant target resource study: `notes/2026-10-13-native-state-codec-budget.md` reports 284,884 bytes for the noncompact writer workspace at target ABI and a reader-only linked codec component size of 15,335 bytes (`.text*` + `.rodata*`, relocatable, not final LTO app). It measured the fixed entry frame of `fm1_state_bin_read` at 8,244 B `-Os` / 8,268 B `-Oz`; this is only that function's fixed entry frame, not complete call-chain high-water or proof of main-stack acceptance. `engines/state/README.md` reports the pull inflater structure about 4,928 B; source header rounds it as about 5.5 KiB including transient decode state. Those estimates describe different scopes; do not add them as an exact firmware stack bound.

The `FM1_STATE_BIN_COMPACT_WRITER` format already streams records and random-access output. Therefore the parser does **not** need replacement merely to read a flash-backed source: `fm1_state_bin_read` takes a range-read callback. Current top-level native restore entry points nevertheless accept a complete `bytes,size` buffer and their callbacks `memcpy` from that RAM buffer. A future flash-backed restore could adapt those callers and preserve existing parser/CRC/decode code, but must handle state staging, exclusive source ownership and the complete apply transaction. No claim that flash-backed load has already been integrated follows from the parser API.

## SAVE/LOAD and transaction constraints

Native SAVE already runs a write-free full collector preflight, then a second stable-state collector pass to the inactive transaction slot. It compares canonical stream fingerprints and headers before committing, and writes the commit marker last; scan verifies the candidate before choosing a generation. Compression cannot move erase earlier or weaken this sequence. A future compact compressor must prove exact representation length and capacity in preflight, repeat deterministically on the second pass, reject overflow before erasing, and preserve the old committed generation on any failed write or validation. If encoded size is not beneficial or does not fit, raw representation must still be accepted under current limits.

On LOAD, keep a declared uncompressed length bounded by the format's whole-file and per-chunk caps; check every output byte against that exact bound, require exact decoder completion/no trailing data, validate integrity before publishing staged app state, and keep recovery selection separate from state mutation. CRC is corruption detection, not cryptographic identity. Since the reader can pull from a callback, use that interface before proposing a custom streaming parser, while redesigning the native callers that currently require contiguous bytes. Workspace sharing with framebuffer SAVE/LOAD/apply stages must be measured against actual lifetimes; linked-global headroom is 2,320 B, so no new heap/full-file buffer is assumed available.

## Other physical flash contents

- **Executable XIP text/rodata:** do not apply transparent compression to code executed in place. It would require decompression into RAM, startup/relocation changes, and additional RAM and latency. The current all-13 linked image is 863,380 bytes against an 868,836-byte budget (5,456 bytes remaining before preserved bank questions); investigate reachability/section savings, not a generic compress-all pass.
- **Immutable read-only tables/assets:** some are already compressed (Braids wave tables); Plaits wave tables have a prior offline lossless compression evaluation but direct-pointer users require full table expansion or a cache/API redesign. The evaluated compressor/decoder path, 83,712 B expansion, and 2,320 B global headroom are documented in `notes/2026-10-12-native-engine-link.md` and `notes/2026-10-14-native-size-savings.md`. Any new table compression needs consumer-specific RAM/timing/code evidence.
- **Packaged demo projects/assets:** compression can reduce distribution/package bytes only if the install or load path understands the representation; read-only packaged content does not become writable project-slot capacity.
- **Stock VM/BTIF/USR/settings/descriptors/key data and preserved sectors:** not free generic capacity. Do not relocate, overwrite or count them as reclaimable without explicit ownership, migration and restore evidence. The current expanded geometry keeps `[0xD9000, 0x100000)` as-is; compression does not change that ownership finding.

`notes/2026-10-14-collector-total-bound.md` calculates a conservative 46,458-byte
ceiling for the current native app's emitted SAVE output. That is a distinct
route to smaller raw slots without relying on compression or reducing musical
state limits. It still needs independent source review and an actual larger
collector/writer/recovery fixture. It does not reduce the generic 98,304-byte
accepted-input cap, admit physical extents, or change the current store contract.

Resolve an exact physical storage ownership map before assigning project extents. If the map cannot provide two 102,400-byte slots, decide whether to enforce a smaller compatibility limit or keep the guarantee unavailable; observed compression ratios do not decide it. If average-space reduction remains valuable after capacity is admitted, prototype reuse of the current DEFLATED chunk format in the compact SAVE writer and flash-backed LOAD adapter. Measure target-linked code, workspace, full stack/callback overlap, time and every accepted dense/incompressible limit; test truncated/corrupt streams, length bombs, power interruption, preflight mismatch, fallback and previous-generation rollback. The current evidence changes no production code, format, physical layout or hardware acceptance.
