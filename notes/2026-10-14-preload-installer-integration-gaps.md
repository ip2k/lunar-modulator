## State at this revision

The chooser and offline build controller exist, but the checked-in page still exports a request JSON. In `sim/web/www/installer-page.js:29-31, 56-59, 64-95, 117-118`, `mountInstallerPage` accepts an optional `buildClient`, defaults it to `null`, and the module entry calls `mountInstallerPage(root)` without injecting a client. Without that injection, the action calls `downloadRequest`; with a client, the code explicitly reports a private diagnostic result and says no installable firmware file is available. `sim/web/www/installer-build-client.js:5, 187-230` has a same-origin `/api/v1/builds` submit/poll client, but no page wiring or artifact download.

`tools/native/export_image_catalogue.py:117-155` emits eight project choices with `default_candidate: false`, pending packed-dependency validation, and a `full_song_default` whose status is `pending`. The `default_profile` selects every non-test module in the exported catalogue (the all-production-engine baseline). The browser selection view may preselect Event Horizon as a proposed selection; that is not an accepted production default. The catalogue correctly sets its installable, native-link, RAM and hardware flags false. Owner acceptance, exact content/dependencies, native full-song playback and SAVE/reload are still independent gates.

The target controller is real but diagnostic-only. `tools/native/build_demo_image.py:87-99` creates a `linked-private-diagnostic` receipt and keeps installable, hardware, playback and full-song-default acceptance false. It prepares the selected project/module profile and links `app.bin`; its result is not an OTA/FWSC package and must not be sent to the flasher.

The service API (`tools/installer_service/api.py:139-...`, `229-...`, `292-349`) validates bounded requests and receipts and exposes POST `/api/v1/builds` plus GET `/api/v1/builds/{id}`. It requires an injected adapter and fixed worker template; existing fake/Docker adapters are local prototypes. Its success response contains the diagnostic summary only. There is no package/artifact download endpoint. The result verifier specifically requires `installable`, `hardware_admitted`, `hardware_tested`, `native_ram_verified`, `native_playback_verified`, and `full_song_default_accepted` to be false. I found no API-key, bearer, cookie, or auth middleware in this app. Opaque IDs make records hard to guess but do not authenticate a user.

The guarded writer is separate and intentionally unwired. `sim/web/www/native-ota-adapter.js:7, 82-100` refuses construction without a caller-supplied `packageAdmission.verify` and validates a verifier-issued record rather than a caller boolean. It requires explicit matching MIDI input/output ports and model identity; `:170-172` requires the OTA-loader role for writes. It never requests MIDIAccess or enumerates ports. No package verifier is currently connected to this adapter, and the diagnostic `app.bin` is not a candidate package. Existing adapter tests use protocol fakes, not hardware acceptance.

The Pages workflow (`.github/workflows/pages.yml:64-...`) builds a static site and exports `demo-image-catalogue.json`; it does not run a dynamic API, reverse proxy, durable job queue, or artifact store. `notes/2026-10-14-installer-build-service-design.md:5-29, 45` already documents the missing deployment/storage/security decisions and explicitly says not to expose diagnostic output as firmware.

## Smallest concrete integration path

1. Keep the current chooser request schema (`buildNativeDemoSelectionRequest`) and catalogue IDs as the client contract. Preserve the all-production default module profile. Keep the full-song default explicitly pending until the owner chooses/accepts the exact composition and device playback plus save/reload pass; a UI preselection is not that decision.
2. Complete the private diagnostic path only after a controlled service host exists: inject `createInstallerBuildClient` into the page with an explicitly configured same-origin API base, deploy the API behind a same-origin proxy, and provide a fixed isolated builder worker, bounded queue, durable private job/result records, expiry and abuse/rate controls. Add authentication/quota or explicit anonymous-service protection before accepting expensive public builds. Do not return app.bin to the browser as an install action.
3. For actual flashing, first create a distinct admitted package pipeline from the exact built app plus preserved stock protected components under the approved expanded layout. Verify package model/version, component hashes, geometry/layout and project/profile/request provenance in an audited package verifier; reject diagnostic app-only artifacts. Serve only a verified immutable package and receipt by build ID, with exact byte length/hash binding, and re-hash in-browser before admission.
4. Only after that verifier supplies the adapters typed admission record should an explicit user gesture request Web MIDI with SysEx permission, let the user choose matching ports, validate current device/OTA-loader identity, and start a guarded transfer. Keep transfer status, cancellation/recovery semantics and power-loss handling explicit. The adapters current fake tests are protocol behavior checks, not install/recovery acceptance.
5. Keep acceptance separate: full default/selectable catalogue tests, exact image/package and stock-component guards, current FM-1 identity/backups, real playback of the accepted full song, settings migration and rollback/recovery verification, and owner listening remain mandatory before calling the default or installer accepted.

This is the shortest honest decomposition: selection → diagnostic build → admitted package → deliberate WebMIDI transfer. Present code implements selection and most of the *private diagnostic* request/result validation, plus an unwired guarded transfer seam. The omitted package/admission boundary is intentional and blocks flashing; wiring the diagnostic endpoint alone would not complete the user-facing install request.
