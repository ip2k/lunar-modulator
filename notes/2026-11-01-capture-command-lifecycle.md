# Capture feedback follows command application

[verified] On baseline `e267d7cd58efef29afb2c0c38562f4878e8106f5`, a panel Capture held behind a full sequencer event buffer lost its feedback at the next UI sync, before the command actually applied. The actual-app regression fills the buffer with 71 accepted automation edits, admits Capture as HELD, and reproduces the premature `cap_sent` clearing on the first render. The take itself remains safe.

The app now tags only a panel Capture in the existing single pending-command slot and brackets its exact core application with feedback snapshots. The panel keeps an admitted request pending through unrelated commands and renders. A BUSY attempt reports `Capture busy / Try again / Take kept`, without automatic retry or a second admission. Successful reset/import cancels the association; a failed import preserves it. The public command admission return values, event-room rule, command ordering and direct-text admission contract remain unchanged. Existing immediate empty, valid, stopped-overlay and clip-limit refusal behavior remains in place.

[verified] The focused actual-app test exercises immediate and delayed valid/refused Capture, unrelated accepted/refused input, input-driven flush, BUSY behind another typed Capture, repeated presses, history and saved-content retention, reset/import cancellation, invalid-import preservation and empty takes.
