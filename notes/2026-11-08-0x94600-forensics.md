# What `0x94600` means: the 2026-10-15 stage-7 install stopped inside the app region of the layout the unit then ran

Settles docs/18 §4 doubt 1. Docs-only; no hardware touched. Evidence is read
from the installable-firmware branch (`origin/feature/2026-10-11@installable-firmware`):
`notes/2026-10-18-fm1-interrupted-write-forensics.md` and its `.json` receipt,
`notes/2026-10-15-restart-resumed-integration.md`, `HANDOFF.md`; and from
docs/01 §2, docs/17 and `notes/2026-10-26-fm1-stock-v15-recovery.md`.
Private replay archives were not re-read here.

## Answer

- **`0x94600` is an absolute flash address** [verified: forensics receipt:
  journal "program" intent, `607744` decimal]. It is the page-program the
  transaction journal intended next; it was never submitted. The last program
  that completed was `0x94500`, the last sector erase `0x94000`
  [verified: receipt, 144 erases `0x5000`..`0x94000`, 2294 programs
  `0x5000`..`0x94500`, 15,923 matched submit/completion pairs].
- **It is not a package offset and not a VM address.** The stage-7 install was
  written by a RAM loader over the unit's then-current layout, FM-1+VA
  (`FM-1_092`): app area up to `0xD9000`, VM shrunk to 64 KB at `0xD9000`
  (docs/01 §2) [verified: that note; the unit ran 092 from 2026-09-29 to
  2026-10-15]. The image being written was a Lunar app bigger than V15's slot
  (docs/18 §3 cites 597,916 B for the dev-kit app), so programming past
  `0x93000` was in-region for that layout.
- **So the install did not write outside the app region of its own layout.**
  The doubt compared a 092-layout write against the V15 boundary `0x93000`,
  which only applies to the layout restored on 2026-10-26. Under V15,
  `0x93000`..`0x94600` is VM, not app; that is what the recovery note means by
  "sectors `0x93000`-`0x94600` still hold bytes from the interrupted install"
  [verified: recovery note; the VM reformat is [inferred]].
- **Nothing below `0x5000` was touched** [verified: receipt, zero mutation
  submits below `0x5000`]; the boot prefix `0x0`-`0x4000` equals the archived
  092 dump, and the directory-commit sector `0x4000` was never erased or
  written (the directory was meant to go last). The protected tail `0xD7000`-end
  was byte-equal between baseline and target and never mutated.
- **Why the unit failed to boot:** an in-place rewrite of a single-bank app
  with the old directory still live is not atomic; a power loss mid-way leaves
  old directory plus mixed code [inferred: forensics note; exact SPL branch
  unproven, and no post-failure readback of that mixed state exists, because
  the 2026-10-26 recovery overwrote it].

## Unexplained residue

- The "protected tail" starts at `0xD7000`, while 092's VM starts at `0xD9000`
  [verified: both numbers in sources]. The two-sector gap `0xD7000`-`0xD9000`
  is unexplained [reported to check: the install tool's range table was not
  re-read; `tools/fm1_sdk_install.py` returned no match on a grep for
  protect/erase/range keywords on the branch, so the policy may live in the
  campaign's allowlist module].
- Whether the stage-7 target's last page ended exactly at `0x94600`+ or went
  further is not recorded in the notes read; only the replay's stopped point.

## Implications for M8 (the first install on the FM-1)

1. **Pin the layout before computing ranges.** The unit is now stock V15
   [verified: identity `FM-1_015`], so app is `[0x4000, 0x93000)` and
   `0x93000`+ is VM. An image sized for 092's layout (past `0x93000`) must not
   be written over V15 without a deliberate VM migration. Derive the write range
   from the identity-read layout, not a constant.
2. **Protect:** `[0, 0x4000)` always (the transporter already refuses it);
   VM `[0x93000, 0xE9000)` under V15; BTIF `0xE9000`, USR `0xEA000`, `key_mac`
   `0xFF000`, and the `cfg`/`cfg_tool` area unless the package owns them.
3. **Atomicity:** the failed design was in-place single-bank, directory last.
   M8 should rely on the proven fallback (docs/17 recovery, Pico 2 W) and
   treat any interrupted write as "recover, do not resume"; resuming a
   journal was the stage-7 plan and is unproven. A bank-swap is not available
   in V15's layout [inferred]. Power must not be removable during the write
   (battery plus the USB cable fixed, owner present).
4. **Record the journal** (intent/submit/completion) as the stage-7 tool did;
   it made this forensics possible.
