# 2026-11-08: fitting the soak image into V15's app slot (lane fit-size)

Wave 1 toward 1.0 (docs/18 M2). Goal: bring the eight-voice soak pipeline image
(`clk320-soak30/cap8-trunc12`, 597,916 B) under V15's 581,564 B app slot with at
least 16 KB to spare (target about 565,000 B), keeping the SRAM heap at or above
the 47,212 B floor, with compiler and linker levers only: no feature removed, no
hot code rebuilt at another level. Nothing was sent to the FM-1 or to the dev
kit; builds ran in the `lunar-jieli-check` container on aeon, host replays in
`lunar-asan`.

## Result

| | `app.bin` B | vs slot 581,564 |
| --- | --- | --- |
| Baseline (rebuilt from the same source) | 597,916 [verified] | overflows by 16,352 |
| **With `--size-profile`** | **570,588** [verified] | **fits, 10,976 B spare** |
| Target | about 565,000 | 16,564 spare |

- **The slot fit is met; the 16 KB margin is not.** 5,588 B more are needed.
  Every remaining lever either changes the code that runs per block, or
  changes a function the perf-levers work placed in SRAM (below). Those were
  not taken: they need a dev-kit soak, which this lane may not run. The
  decision is the owner's (see Owner decisions).
- `.ram0_data` 131,184 B, `.cache_ram_data` 27,180 B, RAM static 474,712 B and
  heap 48,844 B (1,632 above the floor) are unchanged from the baseline
  [verified: `fm1_budget.py`, both ELFs]. `pipeline_bounds` PASS, `audit_link`
  PASS (`late_initcall` exactly `[sdk_meky_check]`).
- The image size depends slightly on the output directory's path length
  (path strings in asserts): the same preparer output in a path one character
  longer was 570,620 B (+32). Quote 570,588 as the figure for the build above.

## What changed, in bytes

The option is `prepare-pipeline-devkit.py --size-profile` (default off, so every
earlier image stays reproducible). It adds `tools/jieli/size-profile.mk` to the
nested engine make and sets `COLDOPT=-Oz`.

| # | Lever | Bytes | Evidence |
| --- | --- | --- | --- |
| 1 | `-D_LIBCPP_DISABLE_EXTERN_TEMPLATE` on Plaits `chord_bank.cc`. Its one `std::sort<float*>` matched libc++'s extern template, which links the whole `libc++.a(algorithm.cpp.o)` (17,342 B); instantiated in the TU, only the sort itself is linked | -16,160 | build e5: 597,916 -> 581,756 |
| 2 | `-Oz` on `mod_script` (text modulation-script parser) | -5,664 | build x-gscript vs e5 |
| 3 | `-Oz` on `seq_cmd` (sequencer command-line interpreter) | -3,872 | x-scmd vs e5 |
| 4 | `-Oz` on `mod_plan`, `mod_registry` (plan builder, name lookup) | about -1,184 | remainder of the combined build after levers 2, 3 and 5; the five-unit group x-gmod measured -1,056 |
| 5 | `-Oz` on `fm1_edit` (editor actions) | -448 | x-u2 vs e5 |
| | **Levers 2 to 5 together** | **-11,168** | final 570,588 vs e5 581,756 |

Levers 2 to 5 are run on an edit, a command line or a script, never inside a
block. No unit called per sample or per block changed its optimisation level
[verified: the unit list in `size-profile.mk`; the hot DSP is built exactly as
before].

## Is the hot code unchanged?

- **SRAM-resident symbols.** All 365 symbols in `.ram0_data` have the same
  name and size in the baseline and the profile build [verified: `nm -S` on both
  ELFs].
- **SRAM-resident code.** The disassembly of `.ram0_data` (44,909 lines) from
  both ELFs, with addresses, relative branch targets, local label numbers and
  XIP addresses masked, is identical in every instruction. The only differing
  lines (219) are in the data tail after the last function (tables that hold
  XIP pointers) [verified: objdump, normaliser in the lane scratch]. The raw
  bytes differ in 1,529 places, which is those masked addresses.
- **XIP code that the profile rebuilds** is the cold list and `chord_bank` (which gets no new opt level, only the define).

## Does the audio still match?

Host replay (clang, ASan and UBSan builds, `LUNAR_REPLAY_CYCLES=57`, cap8, trunc12,
the preparer's source transforms and the image's defines; the soak's
`replay-fit.py` plus a switch that also applies `size-profile.mk` and
`COLDOPT=-Oz`):

| Replay | case hashes | fold | PCM sha256 |
| --- | --- | --- | --- |
| Plain | 228 of 228 equal to the soak's | `4bf911ba` | equal |
| With `size-profile.mk` | 228 of 228 equal | `4bf911ba` | equal (`7b35ce5d4d25...`) |
| ASan against normal | identical in both | | |

This proves the source and the host build of the cold units at `-Oz` give the
same audio. It does not test the pi32v2 code: the target code generation is
**not hash-verified** without a dev-kit run, which this lane may not do. The
argument for the target is the identical SRAM code above plus the fact that the
rebuilt units are not on the audio path. Timing is **not measured**.

## Levers measured and not taken

All against build e5 (extern-template fix only, 581,756 B), one unit or group
at a time, each `-Oz` with the fix. "RAM" means a function the perf-levers work
placed in SRAM changed size.

| Unit(s) | Bytes | Why refused |
| --- | --- | --- |
| `fm1_app` | -7,552 | per-block `fm1_app_pipeline_produce`, `pipeline_convert`, `post_fx_run` are in it; RAM sizes change |
| `fm1_arp` | -5,152 | the arp engine runs per block; three SRAM-resident DX7 functions (`PrepareVoice` -38 B, `Start` +6, `NoteOff` +10) change size too (IPRA register information from the callee) |
| `seq_clip` | -1,696 | holds `sq_swing_delay`, `sq_clip_governing_trig` and other helpers of the per-block sequencer |
| `fx_host`, `mfx_host` | -1,568 | per-block effect hosts (`fm1_mfx_block`) |
| `fm1_seq_ui` | -1,280 | RAM: `fm1_seq_ui_sync` -50 B |
| `fm1_mod_ui` | -1,120 | RAM: same three DX7 functions as `fm1_arp` |
| `mod_mi`, `mod_mi_tables`, `mod_curves` | not measured alone | evaluated each modulation tick (in the x-gmod group) |
| `seq_capture` | -704 | RAM: `fm1_seq_get_info` -122 B |
| `mod_glue` | -32 | RAM: `glue_tick` |
| `state/*`, `fm1_known`, `fm1_meta`, `editor_meta`, `fm1_*_view`, `fm1_app_state`, `fm1_tft`, `seq_persist`, `arp_rhythm`, `midi_fx/registry`, `msfa_tables`, `msfa_rom` | 0 to +64 | no gain at `-Oz` |

The first full group run (a wider cold list, 14,784 B under e5) showed the
RAM-size differences of `fm1_seq_get_info` and the three DX7 functions; the
per-unit runs above found which unit causes each.

## Owner decisions

1. **Reaching the 16 KB margin** (5,588 B short). The measured options are the
   per-block control units above. Taking all of them at `-Oz` would reach
   about 558,000 B or less, but it changes how per-block control code is compiled
   and needs a dev-kit soak (30 minutes, zero underruns, mean load at or below
   85%) before it counts. The alternative is to accept 10,976 B of margin
   (1.9%), because the FM-1 build drops dev-kit-only code and adds the board
   layer anyway (the estimate in `notes/2026-10-29-fm1-image-budget.md` says
   the net is unknown until M3).

## Not done and limits

- No target audio check, no timing measurement (no dev-kit run by instruction).
- The profile is measured on the dev-kit soak image, not an FM-1 link.
- The heap margin (+1,632 B) is the same as before; this lane did not change it
  and it does not carry over to the FM-1 (see the budget note).
- The per-unit table is single-factor against e5; effects are not strictly
  additive (levers 2 to 5 measured -11,168 B together; the singly measured
  parts are -9,984 B for levers 2, 3 and 5 plus about -1,056 for the module
  group).
- Scratch in `/datasets/lunar-modulator/fm1-wave1/fit-size/` on aeon (about the
  SDK copy and 30 build trees) is deleted after this note.
