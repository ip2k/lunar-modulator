### Why a barrier and not a wider fence

The pipelined app fails closed when a UI path (`fm1_app_key`, `_button`,
`_encoder`, `_pitch_bend`, `_all_notes_off`) runs while a block is in flight
(`PIPELINE_GUARD(!pipeline_busy())`): it parks and the unit warm-resets. While
audio streams a block is nearly always in flight, so relaxing the guard per
path is unsafe: the CPU1 worker owns the Macro engine, the Drive inserts and
the Echo and Comp masters, and any UI path may touch them.

So the fence is untouched and the producer drains first
(`lunar_fm1_live_barrier_hold`, `fm1_sdk_main.c produce()`):

1. Before reserving a work slot the producer asks whether the next queued event
   needs a drained app (any key, button, encoder, bend, panic, or a sound 2
   note), or whether the UI's own timer work is due (popup expiry, ARP hold,
   toast, follow, snap), while a block is in flight.
2. If so it does not reserve. The pump loop harvests (the retire runs on CPU0
   in `lunar_pipeline_harvest`), then asks again. Once nothing is pending the
   events are applied in order through the real `fm1_app_*` handlers, the UI
   service runs (`fm1_app_pipeline_service`: `arp_poll`, popup expiry with
   `mod_commit`, `ui_after`), and the block is produced.
3. Notes on sounds 1, 3 and 4 and MASTER stay on the old fast path, applied
   between blocks without a drain. Events apply in order: a barrier event at
   the head stops the drain loop while a block is in flight.

The 8-block output buffer (about 11.6 ms) is what covers the wait. **That
latency is not measured** [inferred]: a drained block costs the producer one
block of lead. It must be measured on the dev kit before the full UI ships.

The shared app's non-pipelined output is byte-identical (the
`tests/test_app_renderer_pipeline.py` hash and the sim tests).

### Soft locks (divergences from R0)

Once blocks run, the pipelined app seals its geometry. In the full UI these
are refused with a popup rather than a reset, and R0 does not do this:

- engine and insert selection (`FM1_APP_SELECT_LOCKED`, shown as "cannot load")
  and effect order ("Effect order is fixed");
- Macro (sound 2) model other than 0 (VA): held at 0 silently in
  `fm1_app_set_param` (no popup), which keeps `pipeline_preflight`'s
  `value[0]==0` requirement from tripping.

PRESETS and ALGORITHM-in-FX therefore do not change an engine on the FM-1
image; on the host the screen otherwise matches R0 (the unit draws none,
above).

## Adversarial review (2026-11-09)

A second session re-read the diff against CLAUDE.md, reran the tests and
rebuilt the images on aeon. Nothing was sent to any device.

Findings:

1. **Fixed: button LEDs ignored the button map.** `lunar_fm1_leds_pack` put
   app button `b`'s LED at physical id `b`; the panel reads button `b` from
   the physical id `j` with `lunar_fm1_button_map[j] == b`. The two agree
   only while the map is the identity, which it is today, but the labels of
   buttons 2..11 are TODO(hardware), so the first correction to the map
   would have lit the wrong LEDs. The pack now inverts the map; a new test
   (`test_button_leds_follow_the_button_map`) pins it. With today's map the
   output is unchanged.
2. **Fixed: a MASTER popup at boot.** The panel's first pot reading asked for
   the popup, so the full-UI image would open "Volume N" (and service its
   expiry) at start-up; the simulator's init sets MASTER without one
   (`sim/web/www/worklet.js`). Only moves show it now.
3. **Corrected in this note: the display.** The FM-1 image draws no app
   screen (`TODO(display)` in `fm1_sdk_main.c`); the earlier text said the
   display layer was wired in #179 and that the screen matches R0.
4. **Corrected: battery threshold source.** Felucca's `ui_draw.c` has
   531/561/591 [verified: local clone b0dcd53]; fm1-nes 870f305 has no
   battery thresholds, so it is no longer cited for them here or in
   `fm1_input.h`. (`firmware/board/README.md` still cites both; left as it
   was, outside this lane.)
5. **Corrected: the Macro lock.** It holds the model at 0 silently in
   `fm1_app_set_param`; it is not a popup.

Checked and found sound: the hold cannot deadlock (it returns 1 only while
busy, and `lunar_pipeline_harvest` retires on CPU0 as soon as CPU1 is done,
`renderer_pipeline_sdk.c`); events stay in order; the panel task (priority
12) busy-waits below the producer (16) on CPU0, so the dwell cannot delay a
block; the LED lines match Felucca's (row bit 1 PA5 to PA9, 2 PA6 to PA10,
3 PA7 to PH6, 4 PA8 to PH9) [verified: Felucca `hal/fm1_input.h` b0dcd53
against `matrix.c leds_on` and `lunar_keys_pack`]; bend scaling matches
