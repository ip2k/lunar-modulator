# 2026-11-09 — M6: audio-path RAM image, run on the AC79 dev kit

Milestone M6 (docs/18): ALNK0 at about 44,118 Hz to the external codec, one
reduced engine voice, per-block timing in a RAM status block and on the TFT,
loaded through the mask ROM like M4/M5. Two images from one source tree
(`firmware/m6/`, README there): `m6.bin` for the FM-1, **built, not run**, and
`m6-devkit.bin`, **run on the AC79 dev kit** through `tools/ram_runner.py`.
§5 is the FM-1 approval request: **NOT APPROVED**.

## 1. The SRAM bound

- **The ROM window is `[0x01C02000, 0x01C07E00)`, 24,064 B.** JieLi's
  24,064-byte USB loader was written there by the mask ROM and ran on this
  FM-1 on 2026-10-26 [verified: `notes/2026-10-26-fm1-stock-v15-recovery.md`,
  M4 note §4]. Nothing has been written above `0x01C07E00` through the ROM;
  the ROM's own data and stack lie above it [inferred].
- **M5's 16 KiB layout cannot hold M6**: with code, a 1,024 B DMA buffer,
  the status block and two 4 KiB stacks, the `m6-plan-2` FM-1 layout ends at
  `0x01C06C70`, 3,184 B past M5's `0x01C06000`, and the kit's at
  `0x01C066B0`, 1,712 B past [verified: `report.json`, review rebuild]. M6 links into
  the whole window: `app.ld` has `LENGTH = 24064` and
  `ASSERT(__ssp_top <= 0x01c07e00)`. `diagnostic_report.py` gained a
  `ram-window` profile (budget 24,064 B); the `ram` profile keeps 16 KiB for
  M4/M5.
- **Exact ranges, build id `m6-plan-2`** [verified: map, `report.json`,

## 2. What the image does

- **Polled ALNK0, interrupts masked** (`cli`; `attach_irq` is a stub). The
  start sequence is #176's `lunar_alnk0_start` against its fixture
  `tests/fixtures/alnk0/lunar_start.json` [verified: host test, the sequence
  equals the fixture's minus the IRQ and delay rows]. Pending is CON2 bit 7,
  acknowledged by writing bit 3; the free half is CON0 bit 15.
- **Stopwatch:** TIMER4 free-running, CON `0x29` (/16, oscillator, run), PRD
  `0x7FFF`. Ticks are 1.5 MHz if the oscillator is 24 MHz, 2.5 MHz if
  40 MHz [inferred]; both readings are reported.
- **Timing accounts:** per block the interval between boundaries, the render
  time, the busy time (render plus report work), late (pending set again
  before the work ended) and missed (a repeated free half, or an interval over
  1.5× the minimum). Report work only runs while the block's age is under
  half the minimum interval. Window sums every 1,024 blocks.
- **Clock words** `SYS_DIV 0x10008`, `CLK_CON0..2 0x1000C..0x10014` are read
  once at entry, never written [verified: WL82.h addresses].
- **Watchdog:** both entries read `P3_WDT_CON` (P33 `0x80`) and, if bit 4
  (enable) is set, set bit 6 (clear) every 256 blocks, as the SDK's
  `wdt_clear()` = `p33_or_1byte(P3_WDT_CON, BIT(6))` [verified: AC79 SDK
  V1.2.13 `cpu.a` `wdt.c.o` IR, lowered with the JieLi toolchain on aeon;
  nothing copied]. Added after run b (§3).
- **FM-1 only:** PA2 backlight on, TIMER4 bound at 40 MHz for the panel waits
  (as M5), the static frame (title, build id), then eight lines — `BLK`,
  `TPB` (ticks per block), `FS24`, `FS40`, `LOAD … MAX …`, `LATE … MISS …`,
  `PCM`, `STEP … RC … F …` — redrawn round robin at most 5 bytes per step.
  Runs until power-off; after a stop the lines stay up.
- **Kit only:** ALNK0's PORTC writes (`0x50080`, `0x50088`, `0x50090`,
  `0x50094`) are dropped and counted. The driver drives PC0, PC1, PC2 and
  PC6 (`LUNAR_ALNK0_PORTC_PINS`); on the kit PC0 is the LCD's TE pin
  [verified: SDK `DevKitBoard.c`, `ui_lcd_platform_data.te_pin`], and PC1,
  PC2 and PC6 are not assigned there, so the mask is conservative. (The
  kit's PC7–PC10 LCD and touch pins are why the FM-1 panel code is left out
  of the kit image, not why these writes are dropped.) Nothing on the kit
  listens to ALNK0, so no audio is heard. 40,960 blocks, a summary, then the M4 P33 reset.

**Fix in #176's code:** `alnk0_audio_mmio.c` was guarded by `__pi32v2__` /
`__GCC_PI32V2__`, the latter from the SDK's CFLAGS, so an SDK-free build
compiled it to nothing and the link failed. The guard now also accepts
`__PI32V2__`, which JieLi clang predefines. This changes that file's hash
recorded in `notes/2026-11-08-alnk0-codec-driver.md` from `4d9facf1…` to
`725e5d63…` (sha256) [verified: review, 2026-11-09]; the code under the
guard is unchanged.

`LUNAR PING`, `ARM`/`ENTER UBOOT`, check `4c4a:8057` at sysfs `3-1.2`, start

What it shows:

- **ALNK0 runs from a ROM-loaded image, polled, on WL82** [verified]: 40,960
  blocks, end 0 (done), 0 late, 0 missed, `alnk0_result` 0.
- **Rate: about 44.1 kHz, not 73.5 kHz** [verified: two host-clock
  bounds, both independent of TIMER4; the exact value is inferred]. 40,960
  blocks of 64 frames take 59.4 s at 44,118 Hz and 35.7 s at 73,529 Hz.
  - The jump's SG_IO returned 60,110 ms after the jump command, with host
    status 3 [verified: `runner/commands.jsonl`]. The runner's SG_IO timeout
    is 3,000 ms (`tools/ram_runner.py`), so the return marks the kernel
    giving up once the kit dropped off the bus, not the reset itself
    [inferred]. The image's own work before the first block and after the
    last is tens of milliseconds (`first_wait` 12,851 ticks, and under
    1,000 UART bytes at 1 Mbaud) [inferred], so about 0.7 s of the 60.1 s
    is that lag. Runs a and b show a lag of the same size: their SG_IO
    returned at 4,709 and 4,710 ms, while the 4 s watchdog below had reset
    the kit within 4 s of the kit application's last kick, which came
    before the jump [inferred]. With a lag between 0 and 1.7 s the rate is
    43.6–44.9 kHz [inferred].
  - The receive-only UART capture of run c [verified: `uart.json`,
    `uart.log`] ran 120 s from 02:02:10.8 UTC and ends with the kit
    application's uptime stamp 52.13 s and no 62.13 s line, so the
    application booted 55.9–65.9 s after the jump (02:02:12.9 UTC, bench
    host clock).
- **Stopwatch ticks:** 2,176.0 per block on average (2,171–2,181), so the
  stopwatch runs at 1.5 MHz and the oscillator is 24 MHz [inferred, from the
  host-timed rate above]. The tick count alone cannot give the rate: if
  TIMER4 and ALNK0 share a clock root, the ratio is the same at any
  oscillator frequency. On the FM-1 the panel's FS24/FS40 lines therefore
  cannot settle it either; the arpeggio's pitch can (A3 at 220 Hz at
  44.1 kHz, about 367 Hz at 73.5 kHz).
- **Timing:** render 251–315 ticks (168–210 µs at 1.5 MHz), 11.6 % of the
  block; busy at most 1,118 ticks (51 %) including the UART report bytes. This
  is the **kit's ROM clock** (`clk_con0 0x1C1`, `sys_div 0`), not 360 MHz.
- **The voice is the host model's**: PCM hash of the first 1,024 blocks
  `0x92CF0315` on the kit equals the host test's [verified].
- **Watchdog:** `wdt_con 0x1C` — the kit's application had armed it (bit 4)
  and it survived the jump into the ROM; kicked, it no longer fires (flags
  `0x48` = pins masked + watchdog armed). The low nibble `0xC` is `WDT_4S`,
  a 4 s period [verified: SDK `include_lib/driver/cpu/wl82/asm/wdt.h`
  table], which fits run b's reset after two windows (about 3–4.5 s in).
  The kit's ROM was entered from the running application (UART
  `ARM`/`ENTER UBOOT`), which is how its watchdog came to be armed.
- **Pins:** 4 PORTC writes dropped (OUT, DIR, PU, PD). Return to the
  application by the M4 P33 reset (`SOFT`); PING answered afterwards.

- **Image:** `m6.bin`, 9,796 B, SHA-256

  `0x01C06C70`; nothing at or above it; all inside the window where the ROM
  ran JieLi's loader on this unit (§1).

  and its clear bit set only if it is armed; clock words read only. No
  matrix scan and no LED code survive the link (only `board_io` and
  `lunar_backlight_on` from the board layer) [verified: `m6.symbols.txt`];
  no flash controller, no eFuse [verified: `audit_link`, disasm].
- **Route:** docs/17's Pico 2 W transporter, UF2 unchanged, with a host tool
  extended from `fm1t_m5.py` (sketch below, not written).
- **Sequence:** as docs/19 for M5 — the owner enters the ROM by docs/17, the
  tool checks the identity and the pinned image, `memw` the three chunks,
  read back, `ramrun 0x01C02000`; the jump will report `ERR jump` because the
  image never returns [inferred, as M5 and the kit runs].
- **What the owner sees and hears:** the frame "LUNAR M6" and `m6-plan-2`,
  then eight lines updating; an A-major arpeggio at −18 dBFS through the
  codec, if ALNK0 alone starts the codec as #176 holds [inferred, strong].
  The owner reads `TPB`, `FS24`/`FS40`, `LOAD`, `LATE`/`MISS` and `PCM` off
  the panel (expected `PCM 92CF0315`) and says whether the tone is clean.
- **Recovery:** a power cycle returns stock V15 (RAM only); if not, docs/17.
  If the watchdog is armed under the FM-1's ROM and the kick fails, a
  watchdog reset boots V15.
- **Watchdog risk before audio:** `main_fm1.c` kicks at entry, after the
  blocking full-frame draw and after the first pass of the lines, then every
  256 blocks. The frame draw (panel setup plus 57,600 pixels over polled
  SPI1) is not measured. On the kit the watchdog was armed with a 4 s period
  (`0x1C`, §3), but only because the kit's ROM was entered from its running
  application. The FM-1's ROM is entered differently: docs/19 Part A keys
  `USB_KEY` with the FM-1 **off** and has the owner switch it on, so V15 does
  not run before the ROM [verified: docs/19 §4 steps 1–3]. A watchdog under
  the FM-1's ROM would therefore have to be armed by the ROM itself, or
  survive a power switch that does not cut the SoC fully (an open point,
  docs/19 §6) [inferred]; neither is known. If it is armed and the frame
  takes longer than its period, the unit resets into V15 before audio
  starts: safe, but M6 would show nothing. Kicking inside the frame draw
  would need a new build (`m6-plan-3`, new hash). **M5's approved image never
  kicks**, so the M5 run will show whether a watchdog is armed under the
  FM-1's cold-entered ROM (a reset to V15 some seconds after the test
  pattern); the kit's result does not predict it.

## 6. Owner decisions

1. **The M6 FM-1 run (§5).** Recommendation: yes, after M5 has run, one RAM
   session with `m6-plan-2`. Without an answer nothing runs on the FM-1.
2. **"Per-block timing at 360 MHz" cannot come from a ROM-loaded image as
   built.** The ROM leaves its own clock (on the kit `clk_con0 0x1C1`,
   `sys_div 0`); reaching 360 MHz needs a PLL and rail switch (trap 12 power
   values), which M6 deliberately does not do. Recommendation: accept timing
   at the ROM clock plus the clock words for M6, and move 360 MHz timing to
   the first image that sets the clock (or to M8). Without an answer the
   docs/18 criterion stays unmet as written.
3. **Output level and test sound:** −18 dBFS, an A3–C#4–E4–A4 arpeggio,
   about 0.74 s per note, until power-off. Recommendation: keep; it is
   quieter than stock's peak [inferred] and changing it changes the hash.
4. **The image exceeds M5's 16 KiB layout** and needs the whole ROM window
   up to `0x01C06C70`. Recommendation: accept the window bound
   `0x01C07E00` (proven by JieLi's loader on this unit).

## 8. Adversarial review, 2026-11-09

An independent review of PR #189 at `d2f1e764` re-checked the build, the
tests and every claim above against its source. No functional defect was
found and neither image changed; the corrections are to this note, the
docs/18 status cell and comments.

- **Rebuild:** `link-diagnostic.sh … m6` with `LUNAR_BUILD_ID=m6-plan-2` on
  the Docker host gave the four hashes in §1 again (`m6.bin` `37334c76…`,
  `m6-devkit.bin` `59fc91df…`, both ELFs), `audit_link` PASS (0 fail, 0
  pending) for both, no `sti`/`rti`, and the §1 ranges and symbol
  addresses [verified]. The shared sources this PR touches do not move the
  earlier images: `m5-test-pattern` with `m5-plan-1` rebuilt to the approved
  `a60410de…` pinned in `fm1t_m5.py`, and `ramtest` with `m4-ramtest-3` to
  M4's `74104cb2…` [verified].
- **Checked and correct:** TIMER4 `CON 0x29` is index 2 = /16 of the
  oscillator, run [verified: SDK `timer/test2.c` `timer_div`]; the clock
  word addresses [verified: `WL82.h` `JL_CLOCK`]; P3_WDT_CON `0x80` and
  `wdt_clear` = bit 6 [verified: SDK `p33.h`, `wdt.h`, the `wdt` example];
  the panel's row offset 40 [verified: `panel_probe.c` RASET]; the image,
  BSS, buffer and stack addresses; the 17-block kit upload; the run b and c
  UART lines quoted in §3 [verified: `uart.log`].
- **Corrected:** the M5-layout overflow (2,448 B was stale; 3,184 B for the
  FM-1 build, 1,712 B for the kit's, §1); the reason the kit drops ALNK0's
  PORTC writes (PC0 is the kit LCD's TE pin; PC7–PC10 are not touched by
  ALNK0, §2); the new hash of `alnk0_audio_mmio.c` (§2); the rate evidence

- **Not changed:** `m6-plan-2` stays the requested image; a kick inside the

- **Tools:** the review, like the lane, read the C by file and grep;
  Rarefaction and Serena were not used.
