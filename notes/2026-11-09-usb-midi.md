# USB-MIDI device in the FM-1 application image (M11)

2026-11-09. Branch `feature/2026-11-09@usb-midi`, from `04f7aa4d` (main after
PR #187). Builds on `notes/2026-11-08-fm1-app-image.md`.

**Result.** With `--usb-midi on` the app image carries a USB-MIDI 1.0 device
that describes itself as stock does: `4C4A:C755`, product "FM-1", full speed,
one MIDIStreaming interface with bulk endpoints 0x84/0x04. Packets from the
host go through `lunar_fm1_usb_midi_packet`, the decoder and router TRS
already uses. It builds with `FM1_GPL_MODS` 0 and 1, and both builds pass
`audit_link.py` and `fm1_budget.py`. **It has not run on the FM-1 or on the
dev kit**, so enumeration itself is [inferred]. The switch is off by default
(owner decision 1 below).

## 1. Route: our own MIT layer on the SDK's low-level driver

The SDK has no MIDI device class:

- `apps/common/usb/device/` has mass storage, HID, CDC, printer, UAC and
  UVC; six of its sources, `descriptor.c` and `usb_device.c` among them,
  include the GPL-2.0 `uac_audio.h`, and none mentions MIDI [verified: SDK
  V1.2.13 tree].
- `usb_stack.h` pulls the Linux-derived `ch9.h`.

So the route is a clean-room layer on the closed driver in `cpu.a`
(Apache-2.0 SDK). It includes only JieLi's `asm/usb.h`, plus the headers
`fm1_sdk_main.c` already uses. The stack's prototypes are declared by hand
in `fm1_usb_sdk.c` from the libraries' IR. The rejected route was porting
the SDK's device framework: it would bring the banned header with it.

What the libraries do [verified: IR of `cpu.a` `descriptor.c.o`,
`usb_setup.c.o`, `usb.c.o`, `vm_sfc.c.o`]:

- **Descriptor hooks.** The descriptor getters are weak, with empty default
  bodies:
  - `get_device_descriptor(u8 *, usb_dev)` (the library then sends 18 B);
  - `get_language_str`, `get_product_str`, `get_iserialnumber_str` and the
    others take `u8 *`, and the length is `ptr[0]`;
  - `usb_get_config_desc` (null gives the default header
    `09 02 00 00 00 01 00 80 C8`).
  - String indices other than 0, 1, 2, 3 and 0xEE stall.
- **Configuration assembly.** `set_descriptor` copies the 9-byte header and
  calls each `desc_config_list` callback. It then fills wTotalLength from the
  bytes written and bNumInterfaces from the callbacks' interface count. A
  callback that returns 0 asserts.
- **Initialisation.** `usb_setup_init` stores the setup and buffer pointers
  and builds the configuration once. It does not clear them, so the glue
  clears its own `usb_setup_t` (100 B) first.
- **Control requests.** A setup hook runs before the standard handling;
  returning 0 lets the library continue.
  - SET_CONFIGURATION(0) disables endpoints 1–4. SET_CONFIGURATION(1) only
    sets the state, so the glue arms endpoint 4 itself.
  - `usb_reset_interface` calls each reset handler with interface −1.
- **Endpoints.** `usb_g_ep_config` with OUT bulk sets a double receive
  buffer, so the receive DMA area is 2 × (64 + 4) B.
- **Writes.** `usb_g_ep_write` spins until TxPktRdy clears. The poll
  therefore writes only when TXCSR shows the endpoint free; otherwise it
  counts the poll as busy and tries again on the next one.
- **Serial number.** `get_norflash_uuid` returns `&flash_info.uuid[0]`,
  which `read_flash_id` fills at flash initialisation.
- **Interrupt.** The control interrupt is IRQ 9 (`IRQ_USB_CTRL_IDX`). The
  glue requests priority 1, below ALNK0's 3 (larger is higher, `asm/hwi.h`),
  so USB never delays the audio interrupt.

Receiving is polled from the panel task; there is no receive interrupt. An
unread OUT packet keeps the endpoint NAKing, so the host waits rather than
losing data [inferred: MUSB behaviour].

## 2. Descriptors, against the stock FM-1

Stock bytes were read from the V15 `app.bin` (581,564 B), which identifies as
`FM-1_015` [verified: bytes]:

| fragment | V15 offset | stock bytes | ours |
| --- | --- | --- | --- |
| device | `0x4e849` | `12 01 00 02 00 00 00 40 4a 4c 55 41 00 01 00 02 03 01` | same, PID `c755` |
| AC interface + header | `0x4e3c0` | `09 04 00 00 00 01 01 00 09`, `09 24 01 00 01 09 00 01 01` | iInterface 0, interface numbers ours |
| MS header | `0x4e711` | `07 24 01 00 01 41 00` | same |
| jacks | `0x4e6ab` | embedded IN 1, external OUT 2, embedded OUT 8, external IN 7 (30 B) | same |
| endpoints | `0x4ea7f` | `09 05 84 02 40 00 00 00 00 05 25 01 01 08 09 05 04 02 40 00 00 00 00 05 25 01 01 01` | same |

- **PID.** The stored device descriptor has PID `0x4155`. Stock reports
  `0xC755` on the bus [verified: bench 2026-09-06], so stock patches the high
  byte at run time: `0x41 | 0x86 = 0xC7` [inferred: the bytes match;
  the patching code was not traced]. Ours stores `c755` directly, and the
  test checks it against stock's bytes with that one change.
- **Interfaces.** Ours has two interfaces (audio control 0, MIDIStreaming 1);
  stock has five, three for UAC audio. That is deliberate: no UAC.
- **AC iInterface.** Ours is 0; stock's is 9. The library serves only string
  indices 0–3 and 0xEE, so index 9 would stall.
- **Strings.** Language US English; product "FM-1". The serial number is
  the first 8 bytes of the flash UUID as 16 upper-case hex digits, as the
  SDK derives it [verified: IR]; whether stock's serial matches it is
  [inferred]. Manufacturer is empty, as stock's device descriptor has
  iManufacturer 0 [verified: bytes].
- **Power.** bmAttributes 0x80 and bMaxPower 0x32 (100 mA), from stock's
  configuration template, not the SDK default's 0xC8.
- **Order.** The wire order of stock's configuration (AC, MS header, jacks,
  endpoints) is [inferred]: the fragments are in separate tables in
  `app.bin`. Ours follows the class specification's order.

`tests/test_fm1_usb_midi.py` (10 tests) compiles `fm1_usb_midi.c` for the
host and checks:

- the descriptors byte for byte against these stock fragments;
- the MIDIStreaming layout: each jack's type, id and source, each
  endpoint's jack, and the MS wTotalLength of 65;
- interface numbering, the strings, the encoder and splitter round trip, and
  the IN batch;
- the glue's include list, its IRQ priority below ALNK0, the TXCSR check
  before every write, the makefile switch, and that the UUID reference is
  strong.

## 4. Size and RAM (V15 slot 581,564 B, SRAM minimum heap 47,212 B)

Built on aeon in containers (session label `wave3-usb-midi`). The serial
fix in §5 is included; the `firmware/fm1/README.md` edit came after these
builds and changes only the build id.

| build | app.bin | slot margin | static RAM | heap | heap over minimum | audit_link | fm1_budget |
| --- | --- | --- | --- | --- | --- | --- | --- |
| off, GPL 0 | 557,532 | +24,032 | 474,784 | 48,716 | +1,504 | PASS (0 fail, 1 pending) | 5/5 PASS |
| off, GPL 1 | 557,532 | +24,032 | 474,784 | 48,716 | +1,504 | PASS (0 fail, 1 pending) | 5/5 PASS |
| on, GPL 0 | 564,732 | +16,832 | 475,612 | 47,884 | +672 | PASS (0 fail, 1 pending) | 5/5 PASS |
| on, GPL 1 | 564,732 | +16,832 | 475,612 | 47,884 | +672 | PASS (0 fail, 1 pending) | 5/5 PASS |

- **Cost.** USB costs 7,200 B of flash and 828 B of RAM. That is why it is a
  switch: the heap margin falls from 1,504 to 672 B. Cache RAM is
  27,180 of 28,672 B in every build.
- **The pending audit item** is the long-standing manual check of
  `sdk_meky_check`'s scheduling; it is the same in every build.
- **Symbol sizes.** Symbols named `usb` total 6,192 B with USB on and 544 B
  without (the SDK's GPIO and power helpers).
- **GPL switch.** The GPL 0 and GPL 1 ELFs are not byte-identical, but
  every size figure above is equal.
- **Baseline.** The 2026-11-08 note's 556,636 B came from an older main.
  The off builds here are the baseline.

## 5. Found and fixed during the link check

The first version declared `get_norflash_uuid` weak. LTO then kept nothing
for it, and the serial number would have read `0000000000000000` on every
unit. The glue now uses a strong reference. In the linked image,
`lunar_fm1_main` passes `flash_info` (`0x01C74188`, where `uuid` sits at
offset 0) to `lunar_usb_midi_string(3, …)` [verified: vendor objdump at
`0x0201c8b4`]. A test keeps the reference strong.

Whether `flash_info` is already filled when USB starts is [inferred]: the SDK
calls `read_flash_id` during flash initialisation, before the application
runs.

## 6. What is not done

- **Not run on anything.** Enumeration, `lsusb -v` and `amidi -l` are
  untested. The dev kit is the next step (§8).
- **MIDI out has no producer.** `lunar_usb_midi_send` and the IN batch
  work, but nothing calls them yet (owner decision 2).
- **No stock OTA update service and no UAC audio.** With this image the
  stock updater cannot reach the unit over USB. Recovery stays docs/17 and
  fail-open, as for the app image without USB.
- **No SysEx either way.** The encoder refuses it, and the decoder drops
  SysEx packets from the host (CIN 4–7) [verified: `fm1_input.c`].
- **The M11 hour-long soak under MIDI** from both inputs needs the image on
  the FM-1 (docs/18 M8).
- **Rarefaction.** `status` ran. `orient` on `lunar_usb_midi_config` with
  `project` set to the worktree found no symbol: its C profile has no
  compile database for `firmware/fm1`. The edits were made without `scope`,
  after reading callers by hand (`fm1_sdk_main.c`, `fm1-app.mk`,
  `prepare-fm1-app.py`).

## 7. Owner decisions

1. **USB on by default?** It is off now because it halves the heap margin
   (672 B left). Recommendation: leave it off until the M6 audio run on the
   FM-1 measures the real heap use, then turn it on.
2. **What should the unit send to the host?** Options: the panel keys as
   notes, the encoders as CC, or nothing until the UI exists.
   Recommendation: the keys as notes on channel 1, a small change in the
   panel task.
3. **Manufacturer string.** Empty, as stock. Recommendation: leave it empty
   so hosts and stock-aware tools see the same device.
4. **Serial number source.** The flash UUID, as the SDK and probably stock
   derive it. A host that remembers the stock unit's port would then see the
   same serial. Recommendation: keep it.
