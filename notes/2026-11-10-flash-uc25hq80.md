# 2026-11-10: the UCUN UC25HQ80 flash on newer FM-1s

Owner request (2026-11-10): detect the newer flash chip on the latest
hardware revision, the UC25HQ80, and stay compatible with it.

**Outcome.** Lunar's Python tools now take the FM-1's flash part from one
allow-list, `tools/fm1_flash_parts.py` (`FM1_FLASH_JEDEC_IDS`): the Puya
P25Q80H (`0x856014`) and the UCUN UC25HQ80 (`0xB36014`). The tools name the
part they find. Any other ID is still refused, including other makers' 1 MiB
parts that end in the same capacity byte `14`. The fail-open timeout bound
now covers the slower of the two parts. No UC25HQ80 unit has been on this
project's bench, so **nothing has run on that part**. Every statement about
it below is [reported].

**What differs in a way that matters.**

1. **No `31h`.** The UC25HQ80 writes SR2 (QE, CMP, SRP1, LB) only through a
   16-bit `01h`. A driver that writes SR2 with `31h` alone leaves SR2
   unchanged on this part. See §3 for JieLi's driver.
2. **Erase is faster, not slower** (10 ms against 20 ms). Every bound that
   must cover both parts uses the worst, 20 ms: `FM1_FLASH_ERASE_MAX_MS`,
   tested in `tests/test_failopen_core.py::test_min_timeout_covers_flash_erase`.
   The fail-open minimum stays 3 s, which the dev kit's 2 s block erase
   sets.
3. **The status-register layout is the common Winbond-style layout**, so code
   that masks BP/CMP/SRP bits does not need a per-part table. That claim
   rests on the UCUN sheet only; the Puya side is not re-checked here.
4. **QE ships clear.** The UC25HQ80 is delivered with its status register
   at `00h`, so QE is 0 (§10.2), and its quad reads need QE set. The FM-1's
   flash bus runs 4-wire (`SPI=4_1_0_0` in V15's `isd_config`, docs/02
   [verified: V15 bytes]), and the SDK driver Lunar links never sets QE
   (§3). Something else must set it on a new unit: factory programming, or
   M-VAVE's SPL. Whether stock V15's SPL does that for a `B36014` part is
   unknown [inferred risk]. fm1-gm reports a new SPL in M-VAVE's V16
   (§1); that this is the reason is a guess, not a finding. Until it is
   known, a package that puts V15's SPL on a UC25HQ80 unit is unproven (§5,
   §6 item 3).

## 3. JieLi's flash driver (SDK V1.2.13)

Read from the bitcode of `cpu.a`'s `vm_sfc.c.o` (Gitee `e30b1ee` = V1.2.13),
disassembled with LLVM 18's `llvm-dis --disable-auto-upgrade-debug-info` in
a throwaway container on the LAN host [verified: IR]. The IR was deleted
after reading and is not in git. This covers the SDK Lunar links. Stock V15
is built on another SDK version and is not covered.

- **No JEDEC table.** Neither `0x856014` nor `0xB36014` appears in the
  object. The ID is read with `9Fh` into `flash_info`. Every use of it either
  returns it (ioctls 100 and 402) or derives the capacity as
  `2^(id & 0xFF)` bytes. That is `0x14`, 1 MiB, for both parts.
- **Commands it sends:** `9Fh`, `4Bh` (then three `00h` address bytes and
  one dummy, and 16 bytes read: the UID, the source of Lunar's USB serial
  number, `firmware/fm1/fm1_usb_sdk.c`), `03h`, `0Bh`, `3Bh`, `6Bh`, `02h`,
  `05h`, `35h`, `01h`, `31h`, `06h`, `50h`, `20h`, `D8h`, `81h`, `C7h`,
  `75h`, `7Ah`, and `42h`/`44h`/`48h` for the security registers at
  `0x1000`/`0x2000`/`0x3000`. All of these except `31h` are in the
  UC25HQ80's command table, the `4Bh` framing and the security-register
  addresses included (Table-7, §9.38) [verified: IR; reported: datasheet].
  (Review, 2026-11-10: the first version of this list left out the reads,
  `02h` and the security-register commands.)
- **Status-register writes** (`flash_write_protect` → `norflash_write_sr`).
  The protected mask is `0x41FC` (BP0–BP4, SRP0, SRP1, CMP). It reads the
  status, and writes only if the masked bits differ: at most three writes
  (`w_cnt` 0, 1, 2), then it gives up. Bit 16 of the request says whether
  SR2 is written at all; without it the write is an 8-bit `01h` (SR1 only).
  With it, the first and third writes are one 16-bit `01h` and the second
  is an 8-bit `01h` followed by `31h`. A caller that sets bit 18 forces the
  `01h`+`31h` form on every write. On a UC25HQ80 that form cannot change
  SR2, so such a call would fail [inferred]. The plain unprotect, ioctl 13
  with argument 0 (`norflash_protect_suspend`), becomes `0x10000`: bit 16
  set, bit 18 clear, so its first write is the 16-bit `01h` the UC25HQ80
  takes [verified: IR]. Which callers pass other values, and bit 18, is
  open: they are not in `vm_sfc.c.o`. The bits written are `0x741FC` of the
  request; QE (S9), LB1–LB3 and the suspend bits are copied from the read
  (`0xBE00`), so this driver never sets or clears QE [verified: IR].
  UCUN's sheet allows an 8-bit or a 16-bit `01h` (§9.6) but does not say
  what an 8-bit one does to S15–S8 [reported: datasheet; open]. (Review,
  2026-11-10: the first version said "three more" retries and "both bytes"
  on every first write.)
- **Busy wait:** `norflash_wait_ok` polls `05h` up to 5,000,000 times. That
  is far longer than either part's 20 ms or 10 ms erase [inferred: each poll
  is a full SPI transaction].
- **4-byte addressing** is entered only for parts above 16 MiB. It does not
  apply to either part.

## 5. Not covered, not verified

- **No UC25HQ80 unit has been on the bench.** No read, dump, write, boot or
  Lunar run has happened on that part.
- **JieLi's USB loader** (`wl82loader.bin`) on a UC25HQ80: whether FC0A,
  reads, erases and programs work is unknown. Other projects report UBOOT
  dumps on new units, but not with this loader [reported, not checked].
- **Stock V15's SPL and OTA loader on a UC25HQ80.** Every Lunar package
  keeps them byte-identical to V15 (`tools/jieli/package_guard.py`). Whether
  they boot and update such a unit, QE included (§2 item 4), is unknown:
  nothing in this lane decoded them.
- **M-VAVE V16 boot area.** fm1-gm reports that V16 brings a new SPL and
  `isd_config`. If newer units ship V16, `tools/jieli/package_guard.py`
  (stock V1.1.9 SPL, V15 files), the V15-only research shim and docs/17's
  restore image do not describe them. Whether UC25HQ80 units ship V16 is
  unknown.
- **The SDK's `31h`-only path** (§3, bit 18): which callers request it is
  not known, and a protection change through it would fail on the UC25HQ80
  [inferred].
- The Puya column of §2 beyond its timings and ID is not re-checked, because
  no Puya datasheet could be fetched.

## 6. Owner decisions raised

1. **Writes on UC25HQ80 units through Lunar's own tools.** Recommendation:
   keep them refused (as now) until someone with such a unit has dumped its
   flash twice, identically, through the same loader. Cost: other owners
   with new units cannot use `fm1_uboot_restore_test.py` (a bench proof
   tool, used on the owner's unit only). The alternative, allowing it now,
   costs a write path that has never run on that part. With no answer:
   writes stay refused.
2. **A second FM-1-transporter patch** so that upstream `fm1t.py write`
   accepts `B36014`. Recommendation: not now. docs/17 is approved for the
   owner's unit, and the V16 boot-area question (§5) would have to be
   answered first. Cost of doing it: a new patch to review and pin, plus
   documentation for a route that has never run on such a unit. With no
   answer: docs/17 stays owner-unit only, as documented.
3. **V16 support** (SPL, `isd_config`, app area `0xA9000`) for any future
   Lunar package. This is a separate stream, needed before Lunar packages
   are offered to owners of new units. Recommendation: open it once V16's
   package has been read and pinned. With no answer: packages stay
   V15-only, as today.
