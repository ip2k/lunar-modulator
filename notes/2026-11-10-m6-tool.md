### Review, 2026-11-10

An adversarial review of this PR, on the same branch. Nothing was sent to
the FM-1, the transporter or the kit; the bench host was only read over ssh.

- **Lengths the transporter reads differently** [verified: source]. The
  transporter parses every `memw`, `memr` and `ldr` length with
  `strtoul(..., NULL, 0)` (`src/transporter_proto.c` at `80c5012`, both
  where core 0 sizes the payload and where core 1 runs the command), so a
  leading `0` is octal there. The allow-list took `(\d+)`, which admitted
  `memw 0x1c02000 04096 …`: 4,096 B to the tool, 32 B (`040`) to the Pico.
  - Bound: the octal reading is never larger than the decimal one, and the
    header's CRC covers the decimal length, so the Pico would answer `ERR
    crc` and write nothing; the rest of the payload would reach its line
    parser as text [inferred: source reading].
  - Reach: the tool's own code formats lengths with `str(int)`, so it never
    writes a leading zero [verified: source, tests]. This was a gap in the
    gate's defence in depth, not a path the tool takes.
  - Fix: `_LEN = [1-9][0-9]{0,3}` for all three lengths; a parametrised
    test of eleven such lines in every mode; the fuzz test asserts
    `int(n, 0) == int(n)` for every admitted length; and a new test drives
    `info` and `dump` through the fake so the changed `ldr` pattern is
    exercised (six chunks, the last 3,584 B).
  - **`fm1t_m5.py` has the same pattern.** Not changed in this PR; the owner
    answered "Patch M5 too" on 2026-11-10 and the patch is its own PR.
- **Bounds aligned with the approved sketch.** The M6 note §5 keeps
  `RAM_END` at `0x01C06000` for the image bytes and adds a separate check of
  the runtime top against `0x01C07E00`. The first version had raised
  `RAM_END` to `0x01C07E00` instead. Harmless (admission also needs the
  exact size and hash), but now as sketched: `RAM_END` is M5's line again,
  `ROM_WINDOW_END = 0x01C07E00`, and the bound check is an explicit `raise`
  at import, not an `assert` that `python -O` would drop.
- **A vacuous test.** `tests/test_devkit_usb_midi.py` checked
  `probe.index('usb_read_rxcount') < probe.index('lunar_usb_midi_poll(…)')`,
  but the first name also occurs in the file's header comment, so the check
  passed whatever the code order. It now indexes the two calls; a scratch
  swap of the two statements makes it fail [verified: run].
- **Mutants with the pin test deselected** (`-k 'not pinned_lines'`), each
  caught by a behavioural test [verified: run]: `_RAM_ADDRS` back to
  `RAM_END`; the M5-lock loop removed; `approved_write_end()` returning the
  image bound.
- **End to end again**, with the real `m6.bin` (`37334c76…`) and the
  unpatched constants, also under `python -O`: the same seven lines after
  `ping`/`status`, SRAM equal over `[0x01C02000, 0x01C04644)`, exit 0; the
  retry refused before the port opened (exit 1) [verified: run].
- **Bench evidence re-read** over ssh, files only [verified]: the four
  SHA-256s above recomputed equal; `usb/uart.bin` holds the six `pass=`
  lines (`rx=4 events=1`, then `rx=64 events=16`, three times), the closing
  `pass=27 rx=4 events=1`, and stats from `received=34` at pass 20 to
  `received=52 sent=52 dropped=0 busy=0` through pass 220; the only error
  lines are the three `unkonw desc 600`; `descriptors.bin` is 119 B, the
  first 18 equal to the test's device descriptor and the other 101 to its
  configuration.
- **docs/20 edits:** the loader reading (§1), the length rule and the
  transporter's 512 B ROM writes (the last one 68 B, unproven on hardware;
  a mismatch stops at the read-back) (§2), timing photographs from the
  jump rather than the switch-on, rows for a stall (the sound stops, `F 4`),
  a stopwatch that never counted (`BLK 0`, `STEP 4`) and a dark panel with
  sound, and docs/19's "ask the owner before Part C" after a V15 reset.

**Not done:** the tool has not touched a transporter or an FM-1. Its use waits

## Part 2: the USB-MIDI device on the dev kit

### What was built

`tools/jieli/prepare-devkit.py --boot-control --usb-midi` (new) adds the
three FM-1 USB sources and `firmware/devkit/usb_midi_probe.c` to the kit
image. The probe starts the device after the 200-tick recovery window and
polls it every 500 ms. Each pass logs `usb_read_rxcount` for the waiting OUT
packet, then does the one read; every event is echoed back.

### The run

Bench host, 2026-11-10, 13:19–13:23 UTC. Unattended, with no button presses.

- **Bench state before the run.** The size-levers lane had just finished on
  the kit, and its own post-run `PING` was acknowledged. The kit was running
  that lane's last image, a tracked-pipeline internal-DAC image, not
  `recover` [verified: its UART log].
- **Waiting for the bench.** The session started only after the bench had
  been idle for 10 minutes: no kit process running and no change in that
  lane's folder, with the lock free.
- **Lock.** One exclusive flock on `~/.lunar-devkit.lock` was held for the
  whole session.

Steps:

1. UART `PING`, acknowledged. UART `ARM`/`ENTER`, acknowledged.
   `4c4a:8057` appeared at `3-1.2`. It was the only JieLi device, and `sg0`
   resolved under `3-1.2`.
2. One application-only install of `usb` (11.6 s), pinned to `3-1.2`, then
   one loader reset.
3. The kit enumerated as `4c4a:c755` at `3-1.2` 3.0 s after the reset.

**What the host saw** [verified: sysfs, `lsusb -v`, `amidi -l`]:

| `bcdUSB` / `bcdDevice` | 2.00 / 0x0100 |

**Descriptors.** The sysfs `descriptors` file, 119 bytes, was compared in a
script with the bytes in `tests/test_fm1_usb_midi.py`:

- the 18-byte device descriptor: equal
  (`12010002000000404a4c55c7000100020301`);
- the 101-byte configuration: equal [verified].

The SDK logged `[USB]unkonw desc 600` three times during enumeration. These
were the only error lines in the whole capture [verified: uncut count]. That
is the host asking for a device-qualifier descriptor (`wValue` 0x0600), which
a full-speed device does not have [inferred], and enumeration went on
normally.

**R1: a short packet followed by a full one.** Three rounds went through the
kit's raw MIDI port, `/dev/snd/midiC3D0`. Each round wrote a 3-byte Note On,
waited 20 ms, then wrote 16 messages (48 bytes, which is 16 four-byte events,
one full 64-byte packet) [verified: UART and the host's reads]:

| Round | Pass with the short packet | Pass with the full packet | Echo |
| --- | --- | --- | --- |
| 0 | `pass=9 rx=4 events=1` | `pass=10 rx=64 events=16` | 51 bytes, equal to what was sent |
| 1 | `pass=15 rx=4 events=1` | `pass=16 rx=64 events=16` | equal |
| 2 | `pass=21 rx=4 events=1` | `pass=22 rx=64 events=16` | equal |

- Each pass read exactly one packet, whole, in the order sent. No event was
  lost or split, and every echo matched byte for byte.
- After a closing All Notes Off (`pass=27 rx=4 events=1`), the counters
  stayed at `received=52 sent=52 dropped=0 busy=0`. They read the same at
  every 10-s report through 112 s.
- Other counters: `configurations=1`, `resets=2` (presumably the host's two
  bus resets during enumeration [inferred]).

**POWER register.** The probe logs the controller's raw POWER register. It
read `0x70` throughout while the host reported 12 Mb/s. On a musb-style
controller bit 4 would mean high speed, so either these bits mean something
else on JieLi's controller or the register is not musb's [inferred].
The host's speed is the authority.

**Back to the normal state.**

1. UART `ARM`/`ENTER` from the USB image, acknowledged. `4c4a:8057` appeared
   at `3-1.2`.
2. Application-only install of `recover` (11.6 s), then one loader reset.
3. Boot 1: `start=build`, image `2d14d093`, 171,344 bytes. The race
   registered four slots; then the planned `irq_hang` fault and the watchdog.
4. Boot 2: `start=continued`. The lock test passed (102,400 rounds, `bad=0`),
   then `healthy=1` at 10.12 s and `stable=1` at 30.12 s. It was still alive
   at 74 s.
5. The final UART `PING` was acknowledged. `3-1.2` is absent, and the kit is
   running `recover` (`2d14d093`) in application mode.

### What this does and does not show

- **Shown** [verified]:
  - the USB-MIDI glue works on AC79 silicon under the V1.2.13 libraries;
  - the stock-shaped descriptors are what a Linux host actually receives;
  - the serial is a 16-digit hex string that is neither zero nor erased flash
    (its source, the flash UUID, is per the code [inferred]);
  - the R1 fix reads a short packet and then a full one whole, one a pass.
- **Not shown:**
  - the FM-1 itself, whose USB wiring and clocking may differ;
  - macOS or Windows hosts;
  - IN traffic at any rate higher than an echo;
  - behaviour across a host suspend or a cable pull;
  - USB audio (UAC1), which this image does not include.
- **M11 in docs/18** (USB-MIDI on the FM-1, an hour under MIDI) is not met by this run;
  the docs/18 row now says the device has run on the kit only.
- **docs/18 §3 item 7** (`--usb-midi` stays off until a hardware run measures heap
  use) is not settled either: this kit image is the SDK's demo app with the
  probe, not the FM-1 app image, so its heap says nothing about the FM-1 build's
  +128 B margin. The probe does not report heap.
