# 2026-11-14 — m5-plan-2: the M5 successor, built and run on the dev kit

`m5-plan-2` (`firmware/m5p2/`) is the image proposed for a second RAM-only run
on the FM-1. It answers the M5 result (`notes/2026-11-10-m5-fm1-ram-run.md`)
with what the kit probes measured (`notes/2026-11-10-devkit-watchdog-probes.md`).
It was built twice with identical hashes, tested on the host, and run four
times on the AC79 dev kit. **Nothing ran on the FM-1 or the Pico transporter.**
A second FM-1 run needs an owner yes for the image hash and for a new host tool
(§6, §7).

## 1. What changed from M5, and why

| Change | Why |
| --- | --- |
| The ROM's watchdog is cleared at entry, then at least every 10 ms in every wait, between spin units, on every pixel row and in the blink loop. The P33 sequence is `lunar_ramtest_wdt_kick`. | The kit's ROM leaves the watchdog armed (`0x1C`, ~4.06 s) [verified, dev kit]. M5 never cleared it, and the FM-1 reset 3.89 s after the jump [verified: M5 note]. |
| PA2 (backlight, active low) is driven before TIMER4, SPI1 or the panel. It then flashes two cadences. | The first sign needs no panel. The cadences measure the clocks from a video (§4). |
| Display-on (`0x29`) is sent right after the panel setup, before the frame. | M5 sent it after the whole frame [verified: `firmware/display/m5_pattern.c`], so a reset mid-frame left the panel dark. |
| The waits keep the 40 MHz binding (2,500 TIMER4 ticks per ms). | As the brief asked. At the kit's 24 MHz oscillator every wait is 1.67 times longer. The cadences show the real ratio. |
| Twelve breadcrumb words at `0x01C05FC0` (`m5p2.h`) record the stage, `WDT_CON` at entry, ticks per block, the longest kick gap, kick counts, the panel result and the elapsed time. | Evidence that survives a watchdog reset into UBOOT (§4, option 2). They are written in every image, inside the M5 window. |
| The marker and mailbox behaviour is a build switch (`LUNAR_M5P2_MAILBOX`), **off** by default. | As the brief asked. Only `main.c` reads the switches; `m5p2.c` is the same object in every image [verified: `test_build_switches_live_only_in_main_c`]. |
| A dead TIMER4 (count stalled for 4,096 polls, or a 10 ms slice not reached in 262,144 polls) switches every later wait to kicked spin loops. A stuck SPI1 gives up after 4,096 polls per byte phase. | Without these limits, a single fault could hold off the kicks [verified: host tests, §3]. |

The image keeps M5's window and budget. The image, BSS and both 4 KiB stacks
end at `0x01C05F10`, and the breadcrumbs take `[0x01C05FC0, 0x01C05FF0)`.
Both lie below `0x01C06000` (`app.ld` asserts all three). `audit_link
--runtime sdk-free` passes for every image [verified].

## 3. Host tests

`tests/test_m5p2_image.py`, 20 tests, compile `m5p2.c` natively and drive it
through a modelled chip. Time is counted in CPU cycles, with 30 per register
access, 300 per P33 byte and 15 per spin. The first two reproduce the kit's
measured 59 µs per kick and ~310 cycles per pixel; the third is the spin cost
measured in §4. The model also has a 15-bit TIMER4 at OSC/16, a P33 frame
decoder and an SPI1 byte decoder with D/C and CS.

The tests check:
- every register access against an allow-list;
- that the first kick and PA2 low come before TIMER4 and SPI1;
- that display-on comes before `0x2C` and the 115,200 data bytes;
- the kick gaps below;
- that the TICKS breadcrumb matches the modelled count within 0.2 %, and
  MAX_GAP within 2 %;
- a dead timer and a stuck SPI;
- the mailbox variant's marker words, P33 writes and silence on UART;
- the kit variant's stubs (no PORTA, PORTH, PORTC, SPI1 or IOMAP bit 4;
  PORTB bit 3 only) and its trace lines;
- the previous-run report;
- the mailbox heartbeats;
- the linker and header constants.

Longest gap between two kicks, modelled (`fm1_run`, one blink cycle):

| CPU / oscillator | Longest gap | Kicks | Note |
| --- | --- | --- | --- |
| 48 / 24 MHz (kit) | 62.7 ms | 2,946 | the 200,000-spin measurement block; the kit measured 59.8 ms |
| 48 / 40 MHz | 62.7 ms | 2,946 | |
| 24 / 24 MHz | 125 ms | 2,946 | |
| 12 / 24 MHz | 251 ms | 2,946 | |
| 6 / 24 MHz | 502 ms | 2,946 | |
| 3 / 24 MHz | 1.00 s | 2,946 | |
| 48 MHz, TIMER4 dead | 62.9 ms | 2,466 | spin waits, five cadence-B flashes |
| 6 MHz, TIMER4 dead | 503 ms | 2,466 | |
| 6 MHz, SPI1 stuck | 502 ms | 1,893 | frame abandoned after one byte, 1 blink |

The gap scales with 1/CPU. Every gap stays under the 4 s watchdog down to a
CPU clock of about 0.8 MHz [inferred: model]. The kit's ROM runs at 48 MHz.

**A bug the kit found and the model then caught.** In the first kit run
(`a-kick`, image `8ae07658…`), cadence B polled TIMER4 once per 100,000
spins. One such unit takes 31.6 ms on the kit, and the 15-bit count wraps
every 21.8 ms at 1.5 MHz, so whole wraps were lost. TIMER4 then reported 379
ms for a 1.25 s half-period [verified: host timestamps]. The kicks were never
late, but TICKS and MAX_GAP undercounted. The model had used 6 cycles per
spin, which kept one unit under one wrap.

The fix:
- `spin_units` now spins in 1,000-spin chunks with a poll between chunks, as
  the measurement does;
- the frame polls every 16 pixels;
- the model uses the measured 15 cycles per spin;
- `test_tick_count_loses_no_wraps` fails on all four clock pairs without the
  fix [verified: reverted and rerun].

The fix grew the image by 32 B. That pushed the stacks into the original
breadcrumb address, `0x01C05F00`, so the link failed on `app.ld`'s assert. The
breadcrumbs moved to the window's last 64 bytes.

## 4. Dev-kit evidence (pre-authorised, unattended)

Bench01. Run folder `~/lunar-m5p2-2026-11-14/` held `probe-run.sh`, the
tools and a run-local `FM1_BENCH_TARGETS` override, all copied from the K1–K3
probe folder. Every tool hash matched this branch [verified]. The override
names only the kit's ROM at `3-1.1` (bus 3), and every run took
`~/.lunar-devkit.lock`.
- `ram_runner.py` pinned `devkit 3-1.1` in every run. It sent only INQUIRY
  ×4, `FB06` ×64, `FD07` ×64 and `FB08` ×4 [verified: `commands.jsonl` of
  all runs].
- The Pico at `3-1.2` and the FM-1 at `1-2` (attached on V15 as `4c4a:c755`)
  were never opened [verified: runner receipts, the targets file].
- UART capture: the Tigard at `3-1.4`, receive-only, 1,000,000 baud, host
  timestamps.

| Run | Image | Entry | Result |
| --- | --- | --- | --- |
| `a-kick` | `m5p2-kit.bin` `8ae07658…` (before the fix) | PING, acknowledged UART ROM entry | survived 27 s with 7,346 kicks; found the lost-wrap bug (§3); SOFT reset to the app |
| `a2-kick` | `m5p2-kit.bin` `0f575a36…` | PING, ROM entry | survived 26.6 s, below |
| `b-mailbox` | `m5p2-kit-mailbox.bin` `7690d684…` | PING, ROM entry | stopped kicking; the watchdog reset into the ROM, below |
| `c-read` | `m5p2-kit.bin` `0f575a36…` | already in the ROM after `b` | read `b`'s breadcrumbs, then a SOFT reset to the app; PING acknowledged afterwards |

**Survival past 4 s by kicks (`a2-kick`)** [verified, dev kit]:
- At entry `wdt_con=0x0000001c` (armed, 4 s, reset mode).
- The image then ran 26.6 s by its own TIMER4 (39,923,886 ticks at 1.5 MHz).
  The host's UART timestamps agree: 26.62 s.
- 7,346 kicks, 0 kick failures. Longest gap 89,732 ticks (59.8 ms), the
  measurement block.
- It ended by its own P33 reset; the kit printed `system reset reason: SOFT`
  and its application's `LUNAR_CONTROL ready=1`.

Timeline from the first UART byte (host clock):

| Stage | s | What |
| --- | --- | --- |
| 1–3 | 0.00 | kick, breadcrumbs, PA2 on, TIMER4 counting |
| 5 | 0.06 | 200,000 spins = 88,414 ticks (58.9 ms) |
| 6 | 4.07 | cadence A: half-periods 656–680 ms (1,000,000 ticks each) |
| 7 | 11.16 | cadence B: half-periods 1.168–1.184 s (about 1,772,000 ticks, 20.04 blocks) |
| 9–10 | 11.53 | panel setup and display-on (stubbed) |
| 11 | 13.29 | frame done (stubbed SPI1: 1.77 s, 241 kicks) |
| 13 | 26.62 | three blink cycles, finish, reset |

**What it says about the clocks** [verified, dev kit]:
- TIMER4 runs at 1.5 MHz, so the kit's ROM uses a 24 MHz oscillator. This
  confirms K1.
- A volatile spin costs 14.1 cycles at 48 MHz in this build (15.1 in the
  first). The model's 15 is within 6 %.

**Mailbox, watchdog reset to the ROM (`b-mailbox`)** [verified, dev kit]:
- The same run up to `finish=stop_kicking`, then heartbeats with no kicks.
- Beat 4 printed at `since_kick=5,002,507` ticks (3.33 s). Beat 5, due at
  4.17 s, never came, so the watchdog fired between 3.3 and 4.2 s after the
  last kick.
- The ROM device was then back at `3-1.1`. The kernel log shows the host's
  storage driver recovering the hung device with a **port reset**, keeping
  device number 40 (descriptor reads `-110`, `-71`, then a good reset). It
  was not a detach and a new device.

**The breadcrumbs survive (`c-read`)** [verified, dev kit]. The kit image,
loaded from that ROM, printed

    LUNAR_M5P2 prev valid=1 0x3250354d 0x0000000d 0x0000001c 0x0001595e 0x00015e84 0x00001cb2
    0x00000000 0x00000000 0x00002404 0x00000003 0x02ad7d92 0xcdafcab2

Decoded, these are `b`'s values:
- magic, and its complement;
- stage 13 (finishing);
- `WDT_CON` 0x1C;
- 88,414 ticks per block;
- max gap 89,732 ticks;
- 7,346 kicks and no failures;
- panel OK;
- 9,220 ms elapsed;
- 3 blink cycles;
- 44,924,306 ticks (the last beat).

So `[0x01C05FC0, 0x01C05FF0)` survived a watchdog reset, the ROM's re-entry
by marker and a second 16-block load session.

**Not shown on the kit:** PA2, SPI1 and the ST7789 stream. They are stubbed
there, because PA0–PA10 and PC7–PC10 are the kit's camera and LCD pins
[inferred: SDK board options]. The panel path has still never run on any
silicon.

## 5. FM-1 clock evidence without a UART: two options for the owner

**Option 1 — video only (default image `m5p2.bin`; recommended first).**
Film the TFT and the LEDs from power-on, with a clock in the frame if you can.

What to expect, if PA2 is the backlight and the clocks are as on the kit:
- The backlight comes on at once.
- Cadence A: three off/on flashes. Each half is `0.4 s × 40 MHz / f_osc`
  (0.67 s at 24 MHz, 0.40 s at 40 MHz).
- Cadence B: three flashes. Each half is 20 measured blocks, about
  `4,000,000 × 14.1 cycles / f_cpu` (1.18 s at 48 MHz).
- The pattern, labelled `m5-plan-2 <WDT_CON hex> <ticks per block hex>`.
  The label alone gives the watchdog state at entry and the CPU/oscillator
  ratio: ticks per block = `200,000 × 14.1 × f_osc / (16 × f_cpu)`.
- The LED code: 3, 2 or 1 blinks per cycle (README).
- On kit clocks the panel comes on about 11.5 s after the jump. A reset back
  to V15 within ~4 s would mean the kicks do not reach the FM-1's watchdog.

From the video: `f_osc ≈ 16 MHz·s / T_A` and `f_cpu ≈ 56 M cycles / T_B`
[inferred: assumes the FM-1 runs this code at the kit's cycles per spin;
same core, same SRAM].

Costs:
- No SRAM is read back, and nothing leaves the window.
- The host tool needs only a new pinned image and a new one-attempt lock
  (§6).
- The image kicks until power-off. The run ends, as before, with the
  owner switching the unit off.
- New against M5's approval: the image writes P33 `WDT_CON`. It writes no
  other P33 register; `PR_PWR` is never written on the FM-1 [verified: host
  tests].
- If neither the backlight nor the panel works, the video shows nothing, and
  the run says only that.

**Option 2 — mailbox breadcrumbs (`m5p2-mailbox.bin`, needs its own yes).**
The same run, but:
- it writes `usb_update_mode\0` at `0x01C7FD80`, outside the window;
- it stops kicking after 18 s nominal (30 s at 24 MHz);
- the armed watchdog then resets the chip into UBOOT with SRAM kept, and the
  host reads the 48 B of breadcrumbs.

What it adds: the stage reached, `WDT_CON`, ticks per block, the longest
gap, the kick counts, the panel result and the elapsed ticks, as numbers,
even if the backlight and the panel show nothing.

Costs and unknowns:
- A write outside the window, to an address the ROM acts on. On the kit the
  marker sent a watchdog reset to UBOOT [verified, K3 and `b-mailbox`]. On
  the FM-1 this is [inferred]; Felucca uses the mailbox for UBOOT entry
  [reported].
- The host tool needs more than a pin: a crumbs read (§6). `fm1t_m5.py`'s
  `memr` covers only the written image.
- The transporter must notice the ROM coming back without a detach. On the
  kit, Linux saw only a port reset (§4). Whether the Pico's host stack
  re-enumerates and answers `status` with `uboot=1` is untested
  [inferred: unknown]. If it does not, the breadcrumbs are lost: `rekey`
  needs the FM-1 off, and power-off clears SRAM [inferred].
- Leaving UBOOT is a power-off, as in Part D of docs/19.
- If the FM-1's watchdog is not armed, nothing resets. The image sits after
  18 s, and the owner powers off; no data comes back.

**Recommendation:** run option 1 first. Choose option 2 only if option 1
shows nothing usable.

`tools/fm1-transporter/fm1t_m5.py` and its approved hash `9673ccd8…` are

  `APPROVED_BUILD_ID = "m5-plan-2"`. `RAM_BASE`, `RAM_END` (`0x01C06000`) and

  `OTHER_RAMRUN_LOCKS = ("fm1t_m5-ramrun.lock", "fm1t_m6-ramrun.lock")`. A run

- Everything else as in `fm1t_m5.py`: no `uboot`, `wsec` or `runapp`, no
  console port, `--loader` refused in `ramrun`, plain-decimal lengths.

Only for option 2, as a separate step:
- admit `b63a643e…` instead, under its own lock;
- add a `crumbs` subcommand that sends `ping`, `status` (must answer
  `uboot=1`) and exactly `memr 0x1c05fc0 48`, then decodes the twelve words.
  It is admitted once, only in a directory that holds the ramrun lock.

## 8. Limits

- The panel path (PA2, SPI1, ST7789) has never run on silicon. The kit
  images stub it, and the host model checks only the byte stream.
- That the kit's pins PA0–PA10, PB7 and PC7–PC10 are unsafe is [inferred]
  from SDK board options, not from the kit's wiring. The kit images never
  touch them.
- That the FM-1's ROM watchdog is the same P33 watchdog is [inferred]. Its
  3.89 s reset matches the kit's ~4.06 s.
- The FM-1 running this code at 14–15 cycles per spin is [inferred].
- The model's costs are fitted to the kit. A different flash/SRAM wait state
  or clock tree on the FM-1 would change the absolute times, not the order of
  operations.
- The breadcrumbs surviving on the FM-1 is [inferred]. On the kit it is
  [verified] at `0x01C05FC0`.
- No arbitrary ROM or SRAM read was used. The breadcrumbs came back through
  the image's own UART trace.
