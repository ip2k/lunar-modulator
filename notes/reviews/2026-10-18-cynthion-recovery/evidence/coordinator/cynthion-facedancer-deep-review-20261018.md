# Cynthion / Facedancer capability review (source-only)

Date: 2026-10-18. Scope: determine whether maintained Facedancer/Moondancer surfaces expose USB PHY line control or host-mode control usable for the FM-1 USB_KEY / SOF recovery sequence. No device, FPGA, USB, SSH, install, or build operation was performed. This is not authorization to replace or operate the currently reviewed key image.

## Result

The stock Facedancer Cynthion backend is a USB **device emulator** controlled by the external USB host. Its RPCs connect/disconnect, bus-reset, configure endpoints, transfer endpoint/control data, and report IRQ events. The inspected API has no arbitrary ULPI register read/write, raw D+/D− state/bit control, target GPIO mapping, VBUS switch, or USB host-controller API. Therefore it cannot emit the project’s USB_KEY transaction or its post-ACK SOF pulse, and neither it nor a generic 1 kHz/50% D+ square wave is validated on the FM-1 as a recovery stimulus.

A PHY-driven implementation is technically plausible but would be new gateware/firmware work, not an existing Facedancer switch. The USB334x supports a 3-pin FS/LS serial mode whose pins carry TX-enable, differential data, and SE0; however LUNA's ordinary ULPI data interface treats the 8 data pins with a common output-enable, while serial mode mixes input and output directions. A safe implementation therefore needs an explicit PHY-mode pin mux / per-pin directions, correct USB334x mode setup and timing, bounded drive/observe/release states, and simulation/electrical review. The PHY differential transmitter is not automatically equivalent to the project’s open-drain-only constraint, especially during an overlapping target ACK. It must not be enabled against the FM-1 based on this research alone.

## Evidence inspected

- Maintained upstream [Facedancer 3.1.3 Moondancer backend](https://raw.githubusercontent.com/greatscottgadgets/facedancer/3.1.3/facedancer/backends/moondancer.py) (release/tag [3.1.3](https://github.com/greatscottgadgets/facedancer/releases/tag/3.1.3), 2026-05-22): `MoondancerApp.connect`, `disconnect`, `reset`, endpoint setup, control/endpoint read/write, and IRQ handling call the GCP device-emulation API. No raw PHY/RX/TX-line or VBUS operation is in this backend.
- Cynthion Moondancer firmware GCP source, current upstream `main` as retrieved 2026-10-18: [moondancer.rs](https://raw.githubusercontent.com/greatscottgadgets/cynthion/main/firmware/moondancer/src/gcp/moondancer.rs). Its `Moondancer` RPC table covers connect/disconnect, bus reset, address/endpoint configuration, endpoint stall/halt, control and normal endpoint I/O, IRQs, and endpoint test setup. The GCP `gpio.rs` class exposes GPIO modes, but only mapped GPIO resources; this is not an arbitrary target-PHY pin API. The inspected Moondancer class has no VBUS or arbitrary ULPI register operation.
- The locally installed Cynthion source is version 0.2.5 (`cynthion-0.2.5.dist-info/METADATA`, SHA-256 `baa184be7ab9b2c3c1388e88283ccd8338af060f62ac02a5ea0a145a3444451a`). Local source pins:
  - `cynthion/gateware/facedancer/top.py`: `bdc0fb4728b2672239377533ca098b27135d7b3cafd90ed4d90e59c2c7f2aa49`. It instantiates LUNA `USBDevice` for the target PHY; the auxiliary and control paths are also composed as USB-device controllers. GPIO0 maps to user PMOD A; GPIO1 provider is commented out; user GPIO maps to the button. No target D+/D− GPIO assignment exists in this top.
  - `cynthion/gateware/platform/cynthion_r1_4.py`: `d874be68494149f685b2314bd7974c934727918f5f7a241e0ae079f1340f91fc`. The target PHY is an ULPI resource (data R2/R1/P2/P1/N3/N1/M2/M1; clock T4); direct target D+/D− N4/P3 are declared input-only monitor resources.
  - `cynthion/boards/cynthion_moondancer.py`: `80c44d188ef827f8f72608f97a215650514e876bc3efed7960690f3e86f724fc`.
  - LUNA `luna/gateware/interface/ulpi.py`: `a56de06f06645aba753674d3ee5972ba747d81838a9cbc99ed165a887fe5a17d`. The `ULPIRegisterWindow` is an internal gateware request/address/data interface. The GCP backend/top does not expose it as arbitrary host RPC.
- LUNA's maintained feature documentation says it has no USB host mode: [features.rst](https://raw.githubusercontent.com/greatscottgadgets/luna/main/docs/features.rst). Facedancer means the Cynthion acts as a USB **device** toward a real external host; it does not make the Cynthion the host.
- USB334x serial-mode source: Microchip [USB334x datasheet](https://ww1.microchip.com/downloads/aemDocuments/documents/UNG/ProductDocuments/DataSheets/USB334x-Data-Sheet-DS00002646A.pdf), §6.6 and Table 6-8. Its 3-pin FS/LS serial mode uses DATA[0] as TX enable, DATA[1] as differential TX/RX data, DATA[2] as TX/RX SE0, DATA[3] as interrupt, and DATA[7:4] driven low. Interface Control register 0x07 bit 1 selects `FsLsSerialMode`; entry also requires transceiver setup per Table 5-1 and has DIR/clock-suspend behavior. This is a PHY feature, not evidence current Cynthion GCP supports it. The mixed pin directions are incompatible with assuming LUNA's common ULPI data OE can simply remain enabled.
- Cynthion's official [Facedancer getting-started guide](https://raw.githubusercontent.com/greatscottgadgets/cynthion/main/docs/source/getting_started_facedancer.rst) uses a Facedancer design/firmware run path. Loading it would replace the current volatile key/diagnostic FPGA image; that is a separate owner-reviewed operation, not done here.
- Local project sources: `tools/cynthion_usb_key/README.md` SHA-256 `0ebb5d5c658aba8e52397db83a80feba977043836c7cce1a4b7ca258bf7e3eea`; `docs/10-usb-key-dongle.md` SHA-256 `b73b4946983d725ae993980edc2528e234e7b5203d77cdc4af9ebecaf6eacc88`. The older staged-operation profile drives through D+/D− GPIO with 1 kΩ series resistors and generates SOF as a 4 µs low pulse each 1 ms. A newer owner-authorized pico-repeat profile at source commit `fef11263` instead uses a finite 16-cycle, fixed-50%-duty PWM train; its 117 tests and routed build passed, but electrical equivalence and FM-1 recovery remain unproven. The docs also retain a 1 kHz square-wave idea as an inferred historical alternative. Neither profile is validated on the FM-1 as a recovery stimulus.

## Useful capability versus limitation

A future disconnected-target experiment could use the official Facedancer design to enumerate an inert, control-only test device on TARGET C to bench01 (the host), while CONTROL remains connected to the Mac for management and TARGET A is empty. This would validate Cynthion’s ordinary USB device-emulation path and host observation only. It would replace the active volatile image and prove nothing about FM-1 ROM acknowledgement. Prefer a purpose-built inert vendor-specific descriptor/function rather than the stock keyboard sample. This requires a separately reviewed owner gate and is not a recovery attempt.

For a PHY-backed recovery waveform, the smallest credible technical direction is a custom bounded gateware sequencer attached to the target PHY, not adding a guessed Facedancer call. It would need exact USB334x mode setup, a mode-specific pin mux/per-pin directions, characterized timing, finite packet/timeout bounds, and automatic return to high impedance on ACK, fault, or timeout. Before any FM-1 test, simulate the sequencer and validate the electrical line waveform on a disconnected fixture with a scope; show that driven levels and contention behavior satisfy the project’s open-drain requirement. The USB334x differential driver may violate that requirement, so an external open-drain buffer or a different mechanism may be required. No such circuit/software compatibility is established here.

## Limits and next dependency

This review is source evidence, not an FPGA implementation or a physical bus measurement. The upstream Cynthion links point at mutable `main`; only the locally installed 0.2.5 files above are hash-pinned. No VBUS, GPIO, PHY mode, endpoint, or host operation was issued. Rarefaction's Python status selected the primary checkout rather than this integration worktree; Serena’s active path was the integration worktree. I used bounded source reads and hashes rather than retargeting either shared semantic service.

Recommended next step: if more control is needed, first have the owner approve a disconnected-target Facedancer enumeration experiment separately from USB_KEY recovery. For any PHY serial-mode proposal, perform an offline pin-direction/timing design review against the exact USB334x and r1.4 hardware, then simulation and disconnected-fixture waveform validation; do not infer FM-1 recovery from either test. No active FM-1 attempt is recommended by this report.
