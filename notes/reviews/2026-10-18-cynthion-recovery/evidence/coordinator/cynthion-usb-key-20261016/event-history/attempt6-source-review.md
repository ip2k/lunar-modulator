# Attempt 6 USB3343 / ACK trace review

Read-only source review; no code, bitstream, or hardware changes. The integration worktree was not retargeted because Serena is concurrently active on a different checkout; Rarefaction reports the primary checkout, not this integration worktree. I verified the relevant source bodies directly.

## Trace and decoder

Attempt 6 is cleaner than attempt 5: the owner reports SAFE was verified after TARGET-A connection, then performed the explicit USER and switch action. It still cannot be called protocol success. The frozen trace (`owner-attempt-6-status.json`, layout 5) ends with `reason=2 / origin=WAIT_DP / terminal=FAULT`, 791 completed packets, ACK snapshot `0x18d` (receiver-live=1, ACK-confirm=1, 99 elapsed ACK ticks), WAIT_DP timeout 500,000 us, SOF=0.

The relevant ring sequence is: at `191655514 us`, GAP records an RXCMD transition to SE0; at `191655674 us`, KEY starts 160 us later with the cached SE0 and GPIO snapshot `0x30` (outputs/OEs on); at `191655774 us`, after 100 us with no intervening RXCMD event, the FSM enters WAIT_DP, still with cached SE0 and GPIO snapshot `0x01` (outputs/OEs off; FPGA pad input DP high, DM low). At `192155774 us`, it faults 500 ms later still reporting cached SE0; GPIO is then `0x00`. No SOF is entered. This repeats attempt 5's exact candidate-ACK → WAIT_DP-timeout pattern, now after a clean owner-reported arm sequence.

The code increments the candidate timer using the cached valid line state while `receiver_live` is latched; it resets on non-SE0 RXCMD updates, but does not require a fresh SE0 update after KEY begins (`gateware.py:223-227,277-287,407-436`). The event ring logs only RXCMD updates and FSM transitions, not periodic samples (`gateware.py:14-53,202-220`; README lines 108-121). Therefore, no event for 100 us means the PHY did not report a line-state change to the adapter during that interval. It does not prove continuous sampling.

The packed GPIO input is at the FPGA pad, on the other side of the Cynthion's 1-kohm series resistor from the target. During active drive, its level is strongly influenced by the FPGA output itself. The high DP GPIO snapshot at WAIT entry cannot prove the FM-1 target-side line was J; it is compatible with an FM-1 clamp low across the resistor, but does not prove one. After release, the later `0x00` GPIO snapshot is likewise not a direct target-side measurement.

## Primary-source checks

The official [Microchip USB334x datasheet](https://ww1.microchip.com/downloads/aemDocuments/documents/OTH/ProductDocuments/DataSheets/USB334x-Data-Sheet-DS00002646A.pdf) supports the current PHY setup and event semantics:

- Register `0x04 = 0x49` is explicitly shown as non-driving mode with full-speed transceiver selection in Table 6-11; §6.5 says OpMode `01` makes DP/DM high impedance while retaining weak ~2 MΩ pulldowns (PDF pages 54, 59; extracted lines 2334–2335, 2557–2560). It is not evidence of a PHY configuration mistake by itself.
- Register `0x39` bit 1 swaps DP/DM, bits 5:4 enable charger pullups, and bits 3:2 preserve UART RegOutput `01`; the selected `0x06` profile sets the board swap and leaves those charger pullups clear (PDF page 75, §7.1.3.5, extracted lines 3111–3133).
- RXCMD is issued on a linestate change and carries current line-state at send time; bits [1:0] encode the linestate. FS/LS mapping is SE0=0, J=1, K=2, SE1=3 (PDF pages 48–50, §6.3.1 and Tables 6-3/6-4, extracted lines 2109–2119, 2133–2142, 2183–2188). This confirms the direction/NXT/low RXCMD field interpretation at the interface level, but cannot certify the exact sampled waveform on this board.
- Read-only Debug register `0x15` contains the PHY's current Linestate[1:0] (PDF page 68, §7.1.1.12, extracted lines 2864–2889).

Project ROM timing material is expressly reported behavior from other JieLi families: the key is 50 kHz / 16-bit MSB-first; the ROM acknowledges by holding both lines low about 1–2 ms, then raises D+ and waits for SOF calibration (`docs/10-usb-key-dongle.md:76-109`). The local ROM model reproduces that sequence but labels it unverified on AC791N (`dongle/sim/jieli_rom.py:1-4,50-68`). It is plausible for ACK to begin on receipt of the final key bit, before the released inter-packet GAP; a new SE0 update after the next KEY state begins is therefore not guaranteed for a real continuous ACK. Requiring specifically a post-KEY-start edge could reject that case. Conversely, ordinary target pulldowns can also yield SE0 in GAP. Neither a GAP SE0 edge nor a 100-us cached-SE0 interval alone identifies its source.

## Conclusion and smallest useful discriminator

The two traces are not sufficient evidence to call the ACK detector false. Attempt 6's clean repetition raises the likelihood that the PHY is seeing a sustained target-side SE0 that suppresses the key-pattern transitions, which is compatible with a ROM ACK clamp across the series resistor. But it is not proof: the candidate timer uses cached SE0, not a fresh in-window transition, and the downstream D+ J transition never reaches the RXCMD cache. The evidence ends at WAIT_DP timeout; it does not prove ROM acceptance, UBOOT entry, or SOF success.

Do not impose a strict “fresh SE0 edge after KEY begins” rule from this trace. The ROM could assert ACK at the end of the preceding key packet / in GAP, and hold it through the next KEY. The minimal source-backed diagnostic for a reviewed future image is a bounded, read-only ULPI read of USB3343 Debug `0x15` at the WAIT_DP timeout, captured alongside cached RXCMD line state, last RXCMD timestamp/age, and current GPIO/OE. If Debug `0x15` differs from the cache, investigate missed RXCMD capture/decoding; if it remains SE0, this only establishes that the PHY's current comparator still sees SE0, not whether the ROM or target bias caused it. A short series of bounded post-release Debug `0x15` samples could check for the reported SE0→J transition without making RXCMD itself the only telemetry, but it must not change the waveform or power/arming policy. The decisive source-vs-pulldown distinction would require target-side electrical observation or independently verified ACK evidence; the FPGA-side GPIO snapshot cannot provide it.
