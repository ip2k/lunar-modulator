## Audio blocks, clocks and sample formats

[verified source] Distinguish producer granularity from hardware IRQ granularity:

| Contract | Vendor | Pinned Lunar |
| --- | --- | --- |
| Render production | 128 frames directly in DMA ISR; signed Q23 | Main-loop `fm1_app_render` produces 64 float frames into queue |
| DMA half | 128 stereo frames | **256 stereo frames**, four 64-frame dequeues |
| Application rate | Header nominal 44,100; hardware constant 44,118 | `fm1_app_init(...,44118.0f)` and content-start rate 44,118 |
| Time source used here | Audio ISR count/period at `0x1eef0f0/4`; budget from opaque `fm1_device_clock()` | TIMER4 free-running 24-MHz contract; raw clock/PLL snapshots and separate calibration diagnostics |
| Transport/simulator | Browser advances at 44,100 and stubs external audio/BLE | Platform `FS` remains 44,100 for USB integration; application uses 44,118 |

Sources [verified]: vendor `app/board/audio.c:27-63,82-111`, `fm1_audio.h:17-21`, `sdk/include/fm1_block.h`; Lunar `firmware/native/app_probe.c:221-280,670-708`, `audio_queue.h:11-17`, `audio_pause.h:12`, Dinghy `src/platform.c:66-73,265-297`, `hal/fm1_time.h`, native `clock_snapshot.h`. Generated probe platform keeps half size but sets HAL master gain unity and disables NOR writes/OTA cleanup (`tools/native/build_application_probe.py:824-862`); examining the vendored platform alone would miss that effective gain.

[inferred arithmetic, not measured latency] At 44,118 Hz, 64/128/256 frames represent about **1.451/2.901/5.803 ms**. Lunar's eight queued blocks hold 512 frames (about 11.605 ms); that is capacity, not observed queue depth or end-to-end latency. Increasing DMA block size cannot increase average engine throughput. Vendor's ISR render and Lunar's main-loop producer have different preemption/deadline models.

[verified source] Lunar already handles NaN as silence and saturates infinities/finite overflow in `lunar_audio_q15`, then queues ±32767 samples (`audio_queue.h:25-43`). Platform scales/clamps Q15 and shifts by 7, documented as a -6 dBFS ceiling; generated unity HAL master avoids applying the physical knob twice. Vendor uses full signed Q23 limits (-8,388,608..8,388,607), gain ramp and USB/BT mixing (`app/audio_output.c:11-39`). [inferred] Directly substituting vendor full-scale Q23 would alter level/precision/headroom. A selected adapter would require explicit gain policy and finite/saturated conversion tests, including negative full scale, NaN/infinity and event offsets across two 64-frame renders. This pilot supplies no audio adapter or gain change.

[verified source] Raw selector snapshots explicitly do not establish CPU MHz (`clock_snapshot.h:6-8,20-22`). Vendor's declared `fm1_device_clock()` implementation is closed; its ISR timer differs from TIMER4 and contains an absolute 80,000-tick short-interval filter (`audio.c:37`). [inferred] Do not transplant that threshold, clock divisor or timer arithmetic without matching the timer's source/rate and live clock evidence. A source constant is not a scope measurement of 44,118 Hz or proof of CPU frequency.

## DMA, interrupts and flash stalls

[verified source] Both use ALNK0 at `0x12e00`, port-C codec pins, 24-bit words and inverted CON0 bit 15 for free-half selection. Vendor enables RX channel 0 for interrupt clock plus TX channel 3, uses 32-byte-aligned receive/transmit/scratch arrays and IRQ 11 priority 4. Lunar uses TX half pending bit `0x80`, 4-byte-aligned output double buffer and audio priority 3; TIMER5 priority 4 scans at 10 kHz and services USB at 2 kHz (`platform.c:224-262,384-389`). Vendor panel TIMER5 IRQ 63 priority 5 is also above its audio priority 4 (`device.c:12-24`). Different numbering does not prove a priority bug. RX enable/ack differences require actual WL82/register/ABI validation, not a mechanical merge.

[verified source] Vendor acknowledges pending at ISR entry, renders to a scratch buffer, masks interrupts for commit, checks half ownership before/after and rejects copies outside a 7/8-block budget. It reports short intervals, overruns and peak ticks (`audio.c:27-63`, `fm1_audio.h:27-47`). Lunar obtains the free half once, dequeues four blocks directly, converts/taps output then acknowledges half (`platform.c:271-297`); queue underflow is counted **per missing 64-frame block** (`audio_queue.h:47-63`). Its diagnostic IRQ profile has inclusive per-source counts and a separate non-double-counted busy total (`irq_profile.h:7-28`), plus producer-gap/render timing in `app_probe.c`. [inferred] Vendor overrun count and Lunar queue underflow are not equivalent units. No same-workload timing trace or target-disassembly comparison was performed, so no DMA race or deadline fix is established.

[verified source] Vendor flash API silences audio and uses cache synchronization; all audio callees/tables require SRAM placement (`fm1.h:15-19,127-138`). Lunar flash driver runs from RAM with IRQs disabled while XIP is unavailable (`hal/fm1_flash.h:3-10`). Timed probe disables NOR admission; SAVE pause stops audio DMA/IRQ and separately requires USB/display quiescence (`audio_pause.h:6-11`). [inferred] Vendor's surviving-audio call graph is not proof Lunar may render safely through a flash operation. Preserve disarmed SAVE and existing source/link/package gates; a RAM annotation on one entry is insufficient.

## LCD and panel comparison

[verified source] Both use SPI1 `0x11d00`, PC7 CS, PC8 D/C, PC9 clock, PC10 data, active-low PA2 backlight and divisor 4. Their ST7789 initialization tables differ: vendor includes offset/window/power/gamma programming while Dinghy leaves voltage/gamma defaults (`app/board/lcd.inc:75-102`; Lunar `src/lcd.c:97-130`). Do not replace an observed panel setup without owner visual acceptance. Panel snapshots, ADC battery/master channels 3/4 and 10-kHz scan give useful independent wiring evidence, not board revision or physical scan proof.

[verified source] Vendor async submit borrows and byte-swaps a RAM band of at most 240×16 pixels; `fm1_screen_pending` checks elapsed 20 ms and on expiry calls a recovery routine that disables SPI, fences, clears count, releases CS, reinitializes and increments a timeout (`lcd.inc:58-73`, `fm1_lcd_hw.h:22-34`). Lunar copies a 240×16 strip into dedicated `cv_px` before DMA so redraw cannot mutate its borrowed source (`app_probe.c:284-310`). Dinghy's blocking wait has a bounded spin count, but only clears pending after a timeout; it does not stop DMA (`hal/fm1_lcd_hw.h:56-66`).

## W7: one precise source-only proposal

[verified control flow] In Lunar `app_probe.c:292-297`, when `lcd_busy` is true and DONE (`0x8000`) stays low, `display_strip` returns through `done` on every call. It never enters `lcd_sync` / `fm1_lcd_wait`, so the HAL's bounded spin timeout cannot release this pending transfer. The strip cursor and source remain held indefinitely. The guard correctly prevents reuse of a potentially active DMA source; removing it would be unsafe. No comment in the inspected path identifies a deliberate sticky fault policy, so intent is unresolved. This conditional liveness failure is reproducible from the source control flow; **no claim is made that DONE has actually stuck on the owner's FM-1**, or that this explains any boot/audio failure.

[inferred proposal] On the separately reconciled native branch, add a wrap-safe pending-transfer deadline to the nonblocking display service. Capture the same monotonic timer at successful submission; before expiry return busy without modifying `cv_px`. On expiry count/report one latched display fault while retaining the DMA buffer, CS and pending ownership. Continue the nonblocking main/audio loop and do not resubmit, fake completion, call the ACK-only blocking wait, or reuse the buffer. This detection-only proposal is useful offline without claiming to abort DMA. Any later abort/restart needs independently reviewed WL82 register ordering and proof the DMA is quiescent before clearing ownership or permitting reuse. The vendor reset sequence is evidence of its implementation, not sufficient hardware evidence for transplanting it. Keep successful transfer behavior, strip order, pixel format and audio producer/IRQ sizes unchanged. Prefer a small independently authored state helper; vendor code need not be copied. If source is imported instead, retain M-VAVE copyright, exact pin, GPL terms and patch record in an attributed subtree; main MIT cannot absorb it as MIT.

Required acceptance [proposed, not run]: deterministic fake-timer/register tests for normal completion, stuck DONE, just-before/at deadline, timer wrap, one latched timeout count, continued main/audio servicing, no resubmission/CS release/source mutation on fault, and no transfer ownership release before separately proven quiescence; confirm generated platform uses this path; real target build/map/disassembly and existing native guards; same-workload display/audio timing comparison with timeout handling enabled. Fault recovery must not spin for a full frame or claim to fix average render load. Actual register semantics, electrical display behavior, timing and physical acceptance remain separate gates.

[inferred] A bounded detection-only state/diagnostic is a plausible source robustness improvement; independent review must decide whether it earns W7 implementation. No runtime abort/restart fix is justified yet. An audio rearchitecture, block-size change or clock write is **not justified** by this comparison. Before implementation the coordinator must reconcile current native display work and assign exact files; this worker owns notes only and made no firmware changes.
